# alerting

Доведение приказа о начале действий от ограниченного круга лиц, принимающих решение,
до удалённых исполнителей — так, чтобы **исполнитель мог сам убедиться в подлинности
приказа**, а посторонний не мог его подделать, повторить или выдать учебное за боевое.

Проектная документация в [`docs/`](docs/), рабочий эталонный прототип в
[`src/alerting/`](src/alerting/).

---

## Главная мысль

**Защищают здесь не секретность, а подлинность и доступность.**

«Эвакуировать корпус А» — не тайна: через минуту это увидят все. А вот поддельный
приказ об эвакуации стоит денег, создаёт давку и разрушает доверие к каналу — после
чего настоящий приказ в следующий раз проигнорируют. И подавленный приказ неотличим от
отсутствия ЧП.

Поэтому весь криптографический бюджет уходит в подписи и проверку, а не в шифрование
тел приказов.

## Как это устроено

1. **Кворум.** ЛПР подписывают приказ ключами Ed25519. Критический приказ требует
   подписей двух **разных людей** — один человек с двумя устройствами не считается.
2. **Сервер не является источником полномочий.** Ключей ЛПР у него нет. Клиенты
   проверяют подписи сами, по корневому ключу организации, закреплённому в устройстве
   при регистрации. Без этого закрепления «проверка на клиенте» была бы театром:
   взломанный сервер просто отдал бы справочник со своим ключом и политику `m: 1`.
3. **Каналы различаются тем, что может проверить получатель.** Приложение получает
   полный подписанный конверт; SMS и голос — только «звонок в дверь» с персональным
   кодом из слов; сирена — только сигнал внимания.
4. **Учебное невозможно спутать с боевым.** Флаг `drill` — обязательное поле внутри
   подписанной нагрузки, без значения по умолчанию, и сирена отказывается играть боевой
   паттерн для учения.
5. **Неполученный приказ замечают.** Подписанные расписки, лестница эскалации по
   каналам, дашборд неподтвердивших.
6. **Журнал с цепочкой хэшей** и внешне публикуемыми головами — для разбора после
   инцидента.

### Чего это НЕ делает

Взломанный сервер всё ещё может **задержать или подавить** оповещение и соврать на
дашборде. Криптография этого не ловит — ловят эскалация, heartbeat по каналам
(реально наблюдается пока только `ws`: у остальных нет провайдера) и
напечатанный резервный порядок. Это принятый остаточный риск, и он проверяется
отдельным тестом.

Подробно — [docs/01-threat-model.md](docs/01-threat-model.md).

## Быстрый старт

```bash
make setup        # venv + зависимости
make test         # весь набор тестов + порог покрытия ядра
make demo         # вся история от начала до конца, за одну команду
```

`make demo` проходит: предложение, которое один ЛПР запустить не может → вторая
подпись → веерная рассылка → проверка на стороне исполнителя по закреплённому корню →
подтверждение → эскалация для того, кто молчит → отбой → проверенная цепочка аудита.
В конце — три атаки, которые конструкция останавливает, и одна, которую не
останавливает.

### Живой сервер

```bash
make db-up        # PostgreSQL: роли, база, миграции
make org-init     # демо-организация; запомните корневой публичный ключ
ALERTING_ROOT_PUBKEY=<b64u> make serve

alerting-approver propose EVAC.BUILDING --real --severity critical \
    --groups fire-wardens --text "Задымление, 3 этаж" --person p-001
alerting-approver sign <order_id> --person p-001    # одной подписи мало
alerting-approver sign <order_id> --person p-002    # кворум → рассылка
alerting-approver status <order_id>

alerting-executor listen --person x-101             # приём и проверка
alerting-auditor  verify --server http://127.0.0.1:8080   # независимая проверка журнала
```

## Структура

```
docs/                  проектная документация и ADR
config/                политика кворума, кодовая книга, лестница эскалации, словарь
src/alerting/
  core/                ЧИСТОЕ ядро: без I/O, без сети, без чтения часов
  server/              FastAPI, PostgreSQL, каналы, эскалация, аудит
  clients/             CLI ЛПР, исполнителя и аудитора
tests/unit/            ядро в изоляции
tests/integration/     сервер, клиенты, сквозные сценарии
scripts/               org_init.py, demo_e2e.py
```

`alerting.core` — доверенная вычислительная база. Он зависит только от `cryptography`,
`pydantic` и стандартной библиотеки, не читает часы (время приходит как `Clock`) и не
делает ввода-вывода. Это проверяется тестом, а не соглашением: благодаря этому одно и
то же решение о доверии принимается одинаково на сервере и на телефоне исполнителя, и
его можно воспроизвести по записанному инциденту.

## Ключевые тесты

| Тест | Что доказывает |
|---|---|
| `integration/test_evil_server.py` | Взломанный сервер, подсунувший свой ключ и понизивший кворум до 1, отвергается клиентом. И что именно он всё-таки может |
| `integration/test_drill_e2e.py` | Учение никогда не включает боевую сирену |
| `integration/test_escalation.py` | Лестница эскалации; невалидная расписка её не останавливает |
| `integration/test_audit_integration.py` | Отказ журнала не блокирует оповещение; в цепочке нет персональных данных |
| `unit/test_verify.py` | Что отвергается, а что лишь помечается предупреждением |
| `unit/test_canonical.py` | Соответствие RFC 8785 и сужения схемой |

## Статус

Эталонный прототип. Работает целиком, но перед эксплуатацией нужно:

- **заменить заглушки каналов на настоящих провайдеров.** Сейчас реально доставляет
  только WebSocket; `push`, `sms`, `voice` и сирена возвращают статус `stub` и ничего
  не отправляют. Это видно в дашборде, и узел откажется стартовать с такой лестницей
  эскалации без явного `ALERTING_ALLOW_STUB_CHANNELS=1`;
- перенести ключи в защищённое хранилище устройств (`keystore.py` — это шов, а не
  решение);
- довести отказоустойчивость до нескольких **узлов**: метрики, канареечный приказ,
  реплика базы и замер RTO. Код к этому готов — несколько процессов уже корректны
  (`--workers N`), — но переключение без наблюдаемости это надежда, а не план;
- провести юридическую проверку раздела о персональных данных.

Всё, что сознательно не сделано, перечислено в
[docs/01-threat-model.md §4](docs/01-threat-model.md) — чтобы это не дописали позже
«ради безопасности».
