# Доверие, роли и жизненный цикл ключей

## 1. Роли

| Роль | Может | Не может |
|---|---|---|
| **ЛПР** (`lpr`) | Единственная роль, которая издаёт приказы: создать предложение, подписать его, дать отбой. Выгружать и проверять цепочку аудита | Запустить в одиночку то, для чего политика требует больше одной подписи; менять политику |
| **Дежурный** (`duty_officer`, временно) | Смотреть обстановку и дашборд, цепочку аудита, вести справочник и контакты | Создавать, подписывать и отменять приказы. Роль будет убрана |
| **Исполнитель** | Получать, проверять, подтверждать (`acknowledged` / `en_route` / `completed` / `cannot_comply`) | Отдавать или отменять приказы |
| **Хранители корня** (двое) | Подписывать бандлы справочника и политики | Подписывать приказы — корневой ключ **никогда** не является ключом ЛПР |

Роль — атрибут записи о ключе в справочнике. Один человек может иметь два ключа с
разными ролями, но один ключ никогда не закрывает кворум выше `warning` в одиночку
(см. `distinct_persons` ниже).

## 2. Кворум

`config/policy.example.yaml`, подписывается корнем:

```yaml
# Кто вообще может одобрять. Обязательное поле без умолчания — политика, не
# называющая одобряющих, должна быть непригодной, а не разрешающей всё.
approver_roles: [lpr]

severities:
  info:         { launch: {m: 2, distinct_persons: true}, cancel: {m: 2, distinct_persons: true} }
  warning:      { launch: {m: 2, distinct_persons: true}, cancel: {m: 2, distinct_persons: true} }
  critical:     { launch: {m: 2, distinct_persons: true}, cancel: {m: 2, distinct_persons: true} }
  catastrophic: { launch: {m: 2, distinct_persons: true}, cancel: {m: 2, distinct_persons: true} }
```

- **`approver_roles`** — список ролей, чьи подписи вообще засчитываются. Это не
  украшение: справочник содержит **все** зарегистрированные ключи, включая устройства
  исполнителей, которые нужны только для подписи расписок. Без этого списка проверенная
  подпись исполнителя молча означала бы полномочие одобрять, и двое исполнителей могли
  бы запустить критическую эвакуацию, а один — дать отбой. Подпись не из разрешённой
  роли отбрасывается (и об этом сообщается), но сама по себе не делает приказ
  недействительным, если настоящие ЛПР его подписали.
- **`distinct_persons`** считает людей, а не ключи. Один человек с двумя
  зарегистрированными устройствами не закроет 2-из-N. Правило двух — про двух людей.
- **Срока у предложения нет.** Оно ждёт второй подписи сколько угодно и всё это время
  видно всем ЛПР в списке «На подпись», с временем создания. Ненужное предложение
  любой ЛПР **отклоняет** (кнопка «Отклонить» в панели и приложении,
  `alerting-approver reject <id>`): подписать его после этого нельзя, кто и когда
  отклонил — на экране и в цепочке аудита (`proposal.rejected`). Ограничения «подписи за N минут»
  (`max_signature_spread_s`) больше нет: человек его не выбирал, а предложение,
  истёкшее за пять минут, пока второй ЛПР шёл к телефону, — это несработавшее
  оповещение.
- **`m`** — сколько разных ЛПР должны подписать, отдельно для каждого уровня и
  отдельно для запуска (`launch`) и отбоя (`cancel`). По умолчанию **двое для любого
  приказа и любого отбоя**, учебного и боевого (ADR 0003): человек выбирает только
  «учение или боевое», а уровень берётся из сценария (его `min_severity`, иначе
  `max_severity`), так что разный кворум по уровням был бы разницей, которую никто не
  выбирал. Меняется в политике (подписать и опубликовать, §5).

  > ⚠️ **Предложение видят все ЛПР** — список открытых предложений отдаёт сервер
  > (`GET /v1/proposals`, ЛПР и дежурному), а не память панели. Прежде панель помнила
  > только созданное через неё и забывала при перезапуске: второй ЛПР с телефона или
  > из другой панели предложения не видел и подписать его не мог.
- **`min_from_role`** — сколько подписей нужно от конкретной роли; при одной роли ЛПР
  не нужно.

Почему обычные мультиподписи, а не пороговые схемы: FROST/MuSig агрегировали бы
подписантов в одну подпись и скрыли, **кто** подписал. Нам нужно ровно обратное.

## 3. Почему сервер полудоверенный — и почему это дёшево

Сервер хранит, упорядочивает, рассылает и журналирует. Ключей ЛПР у него **нет**.
Клиенты исполнителей сами проверяют кворум по **справочнику и политике, подписанным
корневым ключом организации, который каждый клиент закрепил при регистрации**.

Это главное архитектурное решение проекта, потому что без него «проверка на клиенте» —
театр: взломанный сервер просто отдал бы справочник со своим ключом и политику `m: 1`.

Цена: около 200 строк (подписать два JSON-бандла, закрепить один публичный ключ в
каждом клиенте, проверять счётчик версий). Выигрыш: полный взлом сервера понижается с
«противник может эвакуировать любое здание» до «противник может задержать оповещение и
соврать на дашборде».

Тест этого решения — `tests/integration/test_evil_server.py`.

Корневой ключ живёт на двух зашифрованных USB у двух хранителей и используется
несколько раз в год. Это единственное место, где железный токен оправдан уже сегодня.

## 4. Ключи

- **Ed25519**, по ключу на человека и на устройство.
- `key_id = "ed25519:" + b64url(sha256(raw_pubkey))[:22]` — выводится из самого
  ключа, поэтому запись в справочнике не может незаметно подменить материал ключа под
  известным идентификатором.
- Закрытый ключ — в защищённом хранилище устройства (Keychain / Android Keystore /
  TPM). В прототипе — файл, зашифрованный scrypt+AES-GCM
  (`src/alerting/clients/keystore.py`); это **шов, а не решение**, и так в нём и
  написано.

### Регистрация

1. Лично. Проверка документа.
2. Ключ генерируется **на устройстве регистрируемого** и оттуда не уходит.
3. Публичный ключ считывается QR-кодом или зачитывается вслух.
4. Регистрирующий подписывает изменение справочника; публикуется новая версия.
5. **Регистрируемый сверяет, что его `key_id` появился в справочнике, не отходя от
   стола.**
6. Здесь же выдаётся корневой публичный ключ организации для закрепления, карточка
   исполнителя и подписывается уведомление об обработке персональных данных
   ([08-personal-data.md](08-personal-data.md)).
7. Событие `key.enrolled` уходит в цепочку аудита (псевдоним и роль, без ФИО).

Через интерфейс всё это — вкладка «Справочник и ключи» панели (заявка хранителям,
ответ, «Отозвать сейчас») и окно хранителей на компьютере без сети
([13-custodians.md](13-custodians.md), ADR 0013). Команды ниже — то же самое из
консоли.

ЛПР и дежурные, работающие в веб-панели, создают ключ там же: экран «Зарегистрировать
это устройство» показывает публичный ключ и идентификатор, дальше — `directory add`
как ниже. Ключ остаётся в браузере, приказы подписываются там (ADR 0012).

Команды по шагам. Три места: устройство человека, рабочее место дежурного (в сети),
машина хранителей корневого ключа (без сети); между последними двумя файлы носят на
носителе.

```bash
# Рабочее место дежурного: контакт (куда слать) и ключ для слов-подтверждений в SMS.
alerting-org contact set --server https://… --person p-003 --home ~/.alerting \
    --for x-104 --name "Новиков П. С." --phone +7… --site HQ --groups fire-wardens \
    --wake-key-out x-104.wake.hex

# Устройство x-104: ключ рождается здесь. Корневой ключ — с карточки, не с сервера.
alerting-executor enroll --person x-104 --home ~/.alerting --org acme \
    --root-key <с карточки> --wake-key "$(cat x-104.wake.hex)"
#   public key : Y0RXL6s4…   key id : ed25519:3UU6…   — зачитать/QR регистрирующему

# Дежурный: текущий справочник — на носитель.
alerting-org fetch --kind directory --out directory.json --server … --person p-003 --home …

# Машина хранителей: следующая версия, подписанная корневым ключом.
alerting-org directory add --from directory.json --root-key root.key --out next.json \
    --person x-104 --name "Новиков П. С." --role executor --public-key Y0RXL6s4…

# Дежурный: публикация. Сервер проверяет подпись корня и рост версии, как устройство.
alerting-org publish --file next.json --server … --person p-003 --home …
```

`directory add` отказывает, если такой ключ уже есть или у человека уже другая роль
(один человек — одна роль). `directory show --file next.json` печатает справочник
целиком для сверки. Контакт не подписывается корнем: он решает, **кому отправить**
приказ, а не подлинен ли приказ, — устройство всё равно проверяет каждый приказ по
справочнику. Изменения контактов тоже в цепочке (`contact.set`: только псевдоним и
роль — телефон, ФИО, площадка и группы остаются в стираемой таблице контактов).
Повторный `contact set` без `--wake-key-out` сохраняет прежний ключ слов-подтверждений;
с ним выдаётся новый, и его нужно перенести на устройство.

На стенде всё это одной командой: `./docker/person.sh add x-104 "Новиков П. С."
fire-wardens` ([12-docker.md](12-docker.md)).

### Отзыв

Запись переезжает в `revoked[]` новой версии справочника с большим номером. Клиенты
отвергают справочник с версией ниже максимальной виденной, поэтому откатить их на
вчерашний справочник с неотозванным ключом нельзя.

```bash
alerting-org fetch --kind directory --out directory.json …          # дежурный
alerting-org directory revoke --from directory.json --root-key root.key \
    --out next.json --person x-104 --reason "утерян телефон"        # хранители
alerting-org publish --file next.json …                              # дежурный
alerting-org contact remove --for x-104 …                            # больше не слать
```

`--person` отзывает все живые ключи человека, `--key-id` — один (одно устройство из
нескольких). С публикации сервер отказывает этому ключу в каждом запросе и
WebSocket-подключении, устройства перестают засчитывать **все** его подписи — включая
сделанные раньше: держатель украденного ключа мог подписать задним числом. Поэтому
публикация **не блокируется** действующими событиями, которые этот ключ подписал, а
перечисляет их в ответе (`invalidated`, и в записи `directory.published`): их
переиздают оставшимися ЛПР, если событие ещё в силе. Это противоположно политике
(§5), которую сервер отказывается публиковать, если она ломает действующие события:
отозвать украденный ключ нужно сразу, а кодовую книгу можно поменять и после отбоя.

**Целевое время: менее 60 секунд от уведомления кадровой службы.** Это репетируется
с секундомером (см. [07-drills-and-training.md](07-drills-and-training.md)). Если
отзыв занимает трое суток, вся криптография выше — декорация.

### Быстрый отзыв: ключ отзыва дежурной смены

Путь через машину хранителей выше в 60 секунд не укладывается. Поэтому корневой ключ
может назвать в справочнике **ключи отзыва** (`revokers`). Ключ отзыва подписывает
список отзыва — перечень `key_id`, которым больше не доверять, — и **ничего больше**:
он не регистрирует ключи, не продлевает их и не трогает политику. Хранится у дежурной
смены (зашифрованный файл, пароль у старшего смены).

```bash
# Один раз. Дежурная смена создаёт ключ:
alerting-org revoker-keygen --home /srv/revoker
#   public key : TzcE…   key id : ed25519:NNjh…
# Хранители вносят его в справочник (машина без сети), дежурный публикует:
alerting-org directory revoker --add TzcE… --label "дежурная смена" \
    --from directory.json --root-key root.key --out next.json
alerting-org publish --file next.json …

# Звонок кадровой службы — одна команда, секунды:
alerting-org revoke-now --for x-104 --reason "утерян телефон" \
    --revoker-home /srv/revoker --server … --person p-003 --home …
```

`revoke-now` скачивает справочник и текущий список, проверяет оба по корневому ключу,
закреплённому у дежурного, подписывает следующую версию списка и публикует её. Сервер
проверяет список так же, как устройство: подписан ключом отзыва из текущего
справочника, версия выше виденной, ни одна прежняя запись не выпала (список
накопительный). С этого момента ключ получает 403 на каждый запрос, открытое
WebSocket-соединение закрывается в течение 15 секунд, устройства перестают засчитывать
все его подписи и не принимают список с меньшей версией. В аудите — `key.revoked`
с `revoked_with`: каким ключом отзыва.

**Что может украденный ключ отзыва.** Только отзывать — то есть отключить людей. Это
громко (каждый отзыв в цепочке аудита) и не даёт ни подделать приказ, ни заглушить
его тихо. Прекращается корневым ключом: следующий справочник без этого ключа отзыва,
и его список перестаёт действовать везде.

```bash
alerting-org fetch --kind revocations --out revocations.json …
# Ключ отзыва сменили штатно — его отзывы сохранить в revoked[] справочника:
alerting-org directory revoker --remove ed25519:NNjh… --absorb revocations.json …
# Ключ отзыва украли — его список не доверять; настоящие отзывы повторить вручную:
alerting-org directory revoker --remove ed25519:NNjh… --discard-revocations …
```

Команда не даёт убрать ключ отзыва, не решив судьбу его списка. Отзыв корневым
ключом (`directory revoke`) остаётся: он нужен, когда ключа отзыва нет, и при
плановой чистке.

### Ротация и увольнение

Ежегодно, немедленно при смене устройства и при увольнении:

```bash
alerting-org directory retire --from directory.json --root-key root.key \
    --out next.json --person p-002
```

У записи ставится `valid_until`: подписи, сделанные до этого момента, продолжают
проверяться — приказ, подписанный утром уходящим ЛПР, остаётся подлинным, —
но **не засчитываются в кворум новых приказов**, и ключ больше не входит на сервер.
Новое устройство регистрируется как обычно (`directory add` с той же ролью).

## 5. Кодовая книга и политика: как менять

Какие события бывают, что по каждому делать, какие действуют до отбоя и сколько
подписей нужно для запуска и отбоя — всё это одна политика, подписанная корневым
ключом. Не настройка сервера: телефон проверяет её по ключу, закреплённому при
регистрации, и сервер не может её подменить ([ADR 0010](adr/0010-events-until-stand-down-and-signed-codebook.md)).

1. Отредактировать `config/policy.yaml` (кворум) и `config/scenarios.yaml` (события).
2. На машине хранителей, без сети, с корневым ключом:
   ```bash
   alerting-org sign-policy --policy config/policy.yaml --scenarios config/scenarios.yaml \
       --root-key /media/custodian/root-key.SECRET --version 2 --out policy-v2.json
   ```
   Команда печатает корневой публичный ключ — сверить с карточкой хранителей.
3. С рабочего места оператора:
   ```bash
   alerting-org publish --file policy-v2.json --person p-001 --home ~/.alerting/p-001 \
       --server https://alerting.example.internal
   ```
   Сервер примет политику, только если подпись сходится и версия выше текущей.

Панель подхватывает новую политику при обновлении экрана, клиенты — при следующей
синхронизации. На стенде оба шага делает `./docker/policy.sh config/scenarios.yaml`.
