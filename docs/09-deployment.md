# Развёртывание

Один узел, ВМ + systemd, nginx как терминатор TLS, PostgreSQL. Несколько узлов —
фазы 3–7 плана, здесь их ещё нет.

## 0. Что реализовано, а что заглушка

Этот раздел первый намеренно. Документ развёртывания, который начинается с признания,
чего система не делает, — это честная версия, и оператору он нужнее остальных.

| Возможность | Состояние |
|---|---|
| Подписи приказов, кворум M-из-N, проверка на клиенте | **работает** |
| Доставка через WebSocket (приложение исполнителя) | **работает** |
| Цепочка аудита с хешами, подписанные головы | **работает** |
| Лестница эскалации, подписанные расписки | **работает** |
| **push, SMS, голос, сирена** | **ЗАГЛУШКИ.** Возвращают статус `stub`, не отправляют ничего. Узел откажется стартовать, если они есть в лестнице эскалации, без явного `ALERTING_ALLOW_STUB_CHANNELS=1` |
| **Аутентификация HTTP** | **работает.** Каждый запрос подписан персональным ключом Ed25519 над методом, путём, строкой запроса и хешем тела; проверка по справочнику, подписанному корнем. Общего ключа больше нет, отзыв — по человеку ([ADR 0008](adr/0008-signed-http-requests.md)) |
| **Heartbeat по каналам** | **работает** (`/v1/channels/health`), но измеряет ровно столько, сколько есть: по-настоящему проверяется `ws` — есть ли подключённые устройства. У остальных четырёх нет провайдера, и зонд отвечает `stub`, а не «здоров» |
| Хранилище | **PostgreSQL 16.** Журнал аудита защищён от переписывания дважды: правами роли `alerting_app` и триггерами. Миграции версионированы, применяются отдельным юнитом |
| **Несколько процессов** | **работает.** `--workers N` безопасен: счётчик `seq`, окно защиты от повтора, дедупликация сирены и лестница эскалации живут в базе, а по лестнице поднимается только держатель сессионной advisory-блокировки |
| Несколько **узлов**, отказоустойчивость | нет. Всё, что мешало этому в коде, снято; остались наблюдаемость и реплика базы — фазы 6–7 |
| Метрики, канареечный приказ | нет (фаза 6) |

**Следствие для эксплуатации:** сегодня оповещение доходит только до тех, у кого
открыто приложение. Пока каналы заглушены, напечатанный резервный порядок из
`docs/06-runbook.md` §8 — не запасной вариант, а основной для всех остальных.

## 1. Топология

```
        корпоративная сеть
                │  443/TLS
        ┌───────▼────────┐
        │     nginx      │  терминация TLS, лимиты, allow-списки
        └───────┬────────┘
                │  8080, только из подсети прокси
        ┌───────▼────────┐
        │  узел alerting │  systemd; подключается ролью alerting_app
        └───┬───┬────┬───┘
            │   │    │
            │   ▼    │      ┌──────────────┐
            │  5432 ─┼─────▶│  PostgreSQL  │  контакты (ПДн) + цепочка аудита
            │        │      └──────────────┘
            │        │
   сирены (одностор.)│  головы аудита → хост аудиторов
      площадочный VLAN
```

Пользователи до узла приложения не достают — только до nginx.

## 2. Предпосылки

| Что | Почему |
|---|---|
| **NTP (chrony) на узле** | Окно рукопожатия устройства — 60 с, допуск перекоса приказа — ±120 с. Потеря синхронизации времени это **молчаливый полный отказ**: валидные клиенты начнут получать отказ, а узел будет выглядеть здоровым. Юнит не стартует, пока `chronyc waitsync` не пройдёт |
| Сертификат TLS | Для внутренней системы это почти наверняка корпоративный УЦ, а не ACME |
| Пользователь `alerting` без shell | `useradd --system --shell /usr/sbin/nologin --home-dir /var/lib/alerting alerting` |
| **PostgreSQL 16 и две роли** | `deploy/postgres/roles.sql`, один раз суперпользователем. Сервер работает ролью `alerting_app`, у которой по `audit_log` только `SELECT` и `INSERT`; миграции — ролью `alerting_owner`. **Не давайте серверу DSN владельца**: разделение исчезнет, и об этом ничто не сообщит |
| Корневой публичный ключ организации | Сверить **вне канала** с тем, что держат хранители. Не секрет, но подмена пропускает поддельный справочник |

## 3. Раскладка на диске

```
/opt/alerting/releases/<версия>/     распакованный релиз
/opt/alerting/current -> releases/…  симлинк, переключается при обновлении
/opt/alerting/current/venv/          виртуальное окружение с пакетом
/etc/alerting/alerting.env           конфигурация, 0640 root:alerting
/etc/alerting/escalation.yaml        лестница эскалации
/etc/alerting/credentials/           секреты, 0400 root:root
/var/lib/alerting/spool/             записи аудита, не попавшие в цепочку
/var/lib/alerting/heads/             опубликованные головы
/var/backups/alerting/               резервные копии
```

Установка:

```bash
install -d -o alerting -g alerting -m 0750 /var/lib/alerting/{spool,heads}
install -d -o root -g alerting -m 0750 /etc/alerting
install -d -o root -g root -m 0700 /etc/alerting/credentials
cp deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
cp deploy/nginx/*.conf /etc/nginx/conf.d/
cp deploy/env/alerting.env.example /etc/alerting/alerting.env   # заполнить
systemctl daemon-reload
systemctl enable --now alerting alerting-backup.timer
# alerting.service требует alerting-migrate.service, поэтому миграции применятся
# первыми, а узел не поднимется, если они не прошли.
```

## 4. Конфигурация

Полный список — в `deploy/env/alerting.env.example`, раскладка секретов — в
`deploy/env/credentials.README.md`. Здесь только то, что ломается неочевидно.

**Все пути абсолютные.** Относительные считаются от рабочего каталога, и четыре из них
отказывают **молча**:

| Переменная | Что будет при неверном значении |
|---|---|
| `ALERTING_DSN_FILE` | **Отказ старта.** Пустой базы больше не создаётся молча: DSN указывает на существующую базу, а её версию схемы узел проверяет до того, как начать обслуживать. Файл обязан быть `0600` — как и ключи, DSN содержит пароль |
| `ALERTING_WORDLIST` | **Отказ старта** (было: словарь молча пустой и коды побудки не работают) |
| `ALERTING_ESCALATION_CONFIG` | **Отказ старта** (было: молча подставлялась встроенная лестница — другие каналы и тайминги, чем настроил оператор) |
| `ALERTING_HEADS_DIR` | Головы пишутся не туда. Запись обёрнута в `try/except`, поэтому ни старт, ни запрос не упадут; расходятся головы в базе и на диске, а тамперэвиденс держится именно на внешней копии |
| `ALERTING_SPOOL_DIR` | Спул уходит в каталог, который никто не бэкапит. А спул — единственная копия записей, не попавших в цепочку |

### Узел отказывается стартовать, если

- нет `ALERTING_DSN_FILE` (или `ALERTING_DSN`) — подключаться некуда;
- **версия схемы не та**, под которую собран этот релиз, — иначе узел упал бы на
  первом запросе, которому нужна отсутствующая колонка, то есть посреди инцидента;
- нет `ALERTING_ROOT_PUBKEY` — нечем проверить собственные бандлы;
- файл секрета доступен группе или остальным;
- в лестнице эскалации канал без провайдера (снимается `ALERTING_ALLOW_STUB_CHANNELS=1`
  — **никогда в проде**);
- не найден файл лестницы или словаря;
- часы не синхронизированы (`ExecStartPre`).

Проверить конфигурацию, ничего не запуская:

```bash
sudo -u alerting env $(cat /etc/alerting/alerting.env | xargs) \
    /opt/alerting/current/venv/bin/alerting-server --check
```

## 4а. Сколько процессов

```ini
ExecStart=/opt/alerting/current/venv/bin/alerting-server --workers 2 ...
```

Безопасно с фазы 3, и до неё было бы тихой катастрофой. Четыре вещи жили в памяти
процесса, и каждая ломалась при появлении второго:

| Что | Чем стало | Что было бы иначе |
|---|---|---|
| окно защиты от повтора | таблица `stream_seq`, первичный ключ как механизм | у каждого воркера своё окно: повторённый приказ отвергает тот, кто его видел, и принимает тот, кто не видел |
| счётчик `seq` предложений | таблица `streams`, один атомарный upsert | два предложения на одном потоке забирали один номер |
| дедупликация и лимит сирены | таблица `siren_activations` | сирена звучит дважды на один приказ, а снаружи повтор неотличим от второй аварии |
| ролевые ступени эскалации | таблица `escalation_extra` | дежурному звонят дважды |

По лестнице поднимается ровно один процесс — держатель сессионной advisory-блокировки
([ADR 0007](adr/0007-session-advisory-lock-for-escalation.md)). Умер держатель — упало
его соединение — блокировку подхватывает следующий тик другого процесса, без участия
часов и без аренды.

Сколько ставить: воркеры здесь не про пропускную способность, её нужно немного. Два
дают переживание падения одного процесса без паузы на перезапуск. Больше — только если
это показал замер.

## 5. Живость и готовность — это разные вещи

| Эндпоинт | Отвечает на вопрос | Кто спрашивает |
|---|---|---|
| `/v1/healthz` | процесс жив и база отвечает | supervisor |
| `/v1/readyz` | **узел способен разослать приказ**: база, **версия схемы**, оба бандла, словарь нужной длины, воркер эскалации | **балансировщик** |

Балансировщик обязан смотреть на `readyz`. Узел с пустой базой отвечает `healthz: ok`
и не может ничего — это ровно та форма неверной настройки, которую иначе не видно.

Версия схемы проверяется и на старте, и здесь: узел переживает прогон миграций на
общей базе, и балансировщик должен узнать об этом раньше, чем пользователь.

`readyz` отдаёт `503` и называет отказавшую подсистему, поэтому он закрыт
allow-списком в nginx: это подсказка тому, кто прощупывает.

## 6. Запуск, обновление, откат

```bash
systemctl status alerting
journalctl -u alerting -f
```

Обновление:

1. распаковать релиз в `/opt/alerting/releases/<версия>`, собрать venv;
2. `systemctl start alerting-migrate` — миграции применяются **до** переключения
   симлинка, ролью владельца, по одной транзакции на файл;
3. `alerting-server --check` с боевым окружением от имени `alerting`;
4. `systemctl stop alerting` — корректная остановка занимает до 30 с: закрываются
   сокеты исполнителей (код 1012, клиенты переподключаются сразу), дорабатывает
   текущий тик эскалации, публикуется финальная голова аудита, закрывается пул;
5. переключить симлинк `current`;
6. `systemctl start alerting`, дождаться `readyz: ready`.

### Откат и контракт миграций

**Откат — это переключение симлинка обратно, и он безопасен ровно настолько,
насколько соблюдается одно правило.**

Раньше здесь было написано, что откат безопасен, потому что схема создаётся через
`CREATE ... IF NOT EXISTS` и потому совместима назад. С версионированными миграциями
это больше не так, и на этом месте легко потерять данные.

> **Миграции только расширяют.** Новая версия не удаляет и не переименовывает
> колонку и не сужает ограничение. Тогда предыдущий релиз работает на новой схеме —
> он просто не знает про добавленное, — и откат остаётся переключением симлинка.

Убрать колонку можно, но в два релиза: сначала релиз, который перестаёт ею
пользоваться, выкатывается и проживает достаточно, чтобы откат на предыдущий уже не
рассматривался; только потом миграция, которая её удаляет.

Применённый файл миграции **нельзя редактировать**: `migrate` хранит его sha256 и
откажется работать, если он изменился. Иначе два узла сообщают одну и ту же версию
схемы, имея разные схемы, и об этом не скажет ничто.

## 7. Резервные копии

`alerting-backup.timer` раз в сутки. Копируются три вещи:

- **база** — через `pg_dump -Fc` ролью владельца. Владельцем, а не приложением,
  потому что выгрузка обязана содержать триггеры и права: именно они делают
  восстановленную копию такой же запертой, как оригинал. Скрипт после выгрузки
  читает её оглавление и проверяет, что все три сторожа на месте;
- **спул** — единственная копия записей аудита, не дошедших до цепочки;
- **головы** — то, по чему проверяется цепочка.

База содержит ФИО, телефоны и ключи побудки: копия — такие же персональные данные, что
и оригинал (`docs/08-personal-data.md`). `umask 077`, шифровать при вывозе с узла.

**Учебное восстановление раз в квартал.** Критерий прохождения — не «восстановилось»:

```bash
ALERTING_MAINTENANCE_DSN=postgres://alerting_owner@.../postgres \
deploy/backup/alerting-restore-drill.sh /var/backups/alerting/<стамп> auditor-heads.json
```

Скрипт восстанавливает **во временную базу и удаляет её за собой** — учебное
восстановление, способное затереть боевую базу, однажды её затрёт. Дальше он
проверяет, что **все три append-only сторожа пережили восстановление**, и сверяет
цепочку с головами, **которые держат аудиторы**, а не с головами из той же копии.
Внутренняя проверка цепочки не видит обрезанный хвост — для этого головы и
публикуются наружу. Без файла с головами аудиторов скрипт прямо говорит, что учение
неполноценно.

Временную базу создаёт роль владельца, поэтому у неё есть `CREATEDB` и больше ничего
лишнего: учение, требующее суперпользователя, — это учение, которое не проводят.

## 8. Что проверять дежурному

| Что | Как часто | Почему |
|---|---|---|
| `readyz` зелёный | непрерывно | узел может быть «жив» и неспособен разослать |
| `/var/lib/alerting/spool` пуст | ежедневно | непустой = записи аудита падали |
| свежая голова аудита | ежедневно | тамперэвиденс перестал производиться |
| смещение часов < 30 с | непрерывно | на 60 с валидные клиенты начнут получать отказ |
| бэкап отработал | ежедневно | ненулевой выход = тревога |
| сервер работает ролью `alerting_app` | при каждом выкате | проверка в `deploy/env/credentials.README.md`. Узел под ролью владельца может переписать журнал аудита, и ничто об этом не сообщит |
| учебное восстановление | ежеквартально | бэкап, который не восстанавливали, — это надежда |
| список `silent` в `/v1/channels/health` пуст | непрерывно | замолчавший канал должен стать заметен до ЧП. Пока провайдеры заглушены, в списке постоянно четыре канала из пяти — следить надо за `ws` и за состоянием `stale` |

## 9. Сеть

`deploy/nftables/alerting-app.nft`, по умолчанию всё входящее запрещено.

- **вход:** 8080 только из подсети прокси, 22 только с бастиона. Из пользовательского
  VLAN — ничего;
- **выход:** 5432 к PostgreSQL, NTP, DNS, 443 к провайдерам каналов (когда появятся), порт контроллера
  сирен **в одну сторону без обратного пути**, и вывоз голов на хост аудиторов —
  единственный артефакт, который по замыслу покидает машину.

## 10. Чего здесь нет

| Не делаем | Почему |
|---|---|
| Kubernetes | Выбран systemd; `LoadCredential`, sandbox и journald закрывают всё нужное |
| Несколько узлов | Код к ним готов (фаза 3), но нет метрик, канареечного приказа и реплики базы, без которых переключение — это надежда. Фазы 6–7 |
| Реплика PostgreSQL | Фаза 6. Сегодня узел и база — одна точка отказа, и резервный порядок из `docs/06-runbook.md` §8 её и закрывает |
| HSM для ключа сервера | `LoadCredential` + 0400 — верная точка на кривой. Железный токен оправдан для **корневого** ключа, и он на этой машине не живёт |
| Docker | Незачем при systemd: тот же процесс, меньше слоёв |
| Метрики и канарейка | Фаза 6 |
