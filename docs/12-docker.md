# Развёртывание в Docker

Один узел приложения и PostgreSQL на одной машине, через `docker compose`. Это
быстрый путь для стенда и показа. Контур из пяти машин с резервом базы —
[11-installation.md](11-installation.md), через systemd.

Проверено 20 октября 2026: сборка, `org-init`, запуск, учебный приказ от
предложения до проверки исполнителем и `alerting-auditor verify` — `chain intact`.

## 0. Что нужно на сервере

- Docker 24+ с плагином `compose`;
- **синхронизированные часы** (chrony на хосте): контейнер берёт время хоста, а
  при расхождении больше ±120 с узел начинает отвергать валидные приказы и при этом
  выглядит здоровым;
- nginx на хосте с TLS — сервер слушает только `127.0.0.1:7070`, панель —
  `127.0.0.1:7071` (порты — `ALERTING_PORT`, `ALERTING_PANEL_PORT` в `docker/.env`).
  Оба публикуются под **одним доменом** готовым `deploy/nginx/alerting-one-domain.conf`
  (§8).

## Одной командой

```bash
git clone https://github.com/pavel-yamal/alerting.git && cd alerting
./docker/up.sh
```

Собирает образ, поднимает базу, при первом запуске создаёт демо-организацию,
вписывает её корневой ключ в `docker/.env`, запускает сервер и проверяет `readyz`.
Повторный запуск ничего не стирает: он пересобирает образ и перезапускает то, что
изменилось. Начать с нуля — `./docker/up.sh --reset` (стирает базу, ключи и журнал).

Приказы — через `./docker/cli.sh`, он сам подставляет сервер, каталог ключей по
`--person` и демо-пароль:

```bash
./docker/cli.sh alerting-approver propose TEST.PING --drill --severity info \
    --groups fire-wardens --text "проверка" --person p-001
./docker/cli.sh alerting-approver sign <id> --yes --person p-001
./docker/cli.sh alerting-executor sync --person x-102
./docker/cli.sh alerting-executor verify <id> --person x-102
./docker/cli.sh alerting-auditor verify --person p-001
```

Если сборка не может скачать зависимости:

| В выводе | Что делать |
|---|---|
| `Connection reset by peer`, `Could not find a version ... hatchling` | pypi.org недоступен с сервера. Зеркало или внутренний Nexus/Artifactory: `ALERTING_BUILD_FLAGS="--build-arg PIP_INDEX_URL=https://<зеркало>/simple" ./docker/up.sh` (для http-зеркала добавьте `--build-arg PIP_TRUSTED_HOST=<хост>`) |
| `CERTIFICATE_VERIFY_FAILED` | прокси подменяет сертификат: `ALERTING_BUILD_FLAGS="--secret id=ca,src=/path/corp-ca.crt" ./docker/up.sh` |
| `Name or service not known`, `Failed to establish` | у сборки нет сети; если на хосте прокси — `--build-arg HTTPS_PROXY=$HTTPS_PROXY --network host` |

### Панель дежурного

`up.sh` поднимает и веб-панель: **http://127.0.0.1:7071** (порт — `ALERTING_PANEL_PORT`).

**Ключ на устройстве (как в боевом контуре).** На экране входа — «Зарегистрировать
это устройство»: идентификатор, пароль; ключ создаётся в браузере, на экране —
публичный ключ и его идентификатор. Регистрирующий вносит его в справочник:

```bash
ROLE=director PUBLIC_KEY=<публичный ключ с экрана> ./docker/person.sh add p-010 "Орлова Е. В."
```

Дальше человек входит ключом этого устройства и паролем; приказы подписываются в его
браузере. Ключ работает только по **https://** или на localhost: с другой машины —
через обратный прокси с TLS (§8) или `ssh -L 7071:127.0.0.1:7071 <сервер>`.

**Демо-вход** (`ALERTING_PANEL_DEMO_KEYS=1`, по умолчанию на стенде): `p-001`,
`p-002`, `p-003` (ЛПР), `p-004` (дежурный, временно: только смотрит), пароль `demo`. Здесь ключи
лежат на сервере и расшифровываются панелью — для показа, не для работы.

В панели у ЛПР — пошаговая форма: что случилось, учение или боевое, уровень (если
у события их несколько), пояснение. Выбирать получателей не нужно: рассылка одна —
всем зарегистрированным получателям, а боевые оповещения ещё и в публичную
RSS-ленту (§10). Дальше — проверить и подписать, увидеть, сколько подписей ещё
нужно, а после рассылки — кто подтвердил и кто молчит; там же отбой. Для
критического приказа нужны два разных ЛПР: войдите вторым из другого браузера или с
другого устройства.

Дежурный видит ту же обстановку в режиме просмотра: что действует, что ждёт подписи,
история и ход оповещения, но формы создания, подписи и отбоя у него нет.

Подробнее — §8.

### Справочник, заявки хранителям, отзыв — в панели

Вкладка **«Справочник и ключи»** (для дежурного и ЛПР): кто в справочнике и в каком
состоянии; «Добавить человека» (публичный ключ — с экрана регистрации его
устройства, плюс контакт для оповещений); вывод и отзыв ключей; ключ отзыва дежурной
смены (создаётся в браузере) и **«Отозвать сейчас»**; кодовая книга. Изменения
собираются в **заявку хранителям** (файл), подписанный ими ответ загружается обратно
и публикуется. Как работают хранители — [13-custodians.md](13-custodians.md).

**Перенос стенда на ключ хранителей.** Пока корневой ключ лежит на сервере (демо),
доступ к серверу — это полный контроль. Перенос: хранители создают ключ в окне
хранителей, дежурный выгружает любую заявку, хранители подписывают её как перенос,
администратор сервера выполняет `./docker/rotate-root.sh <файл ответа>`. После этого
`person.sh add/revoke` отказываются — всё идёт через панель и хранителей.

### Свой список событий

```bash
cp config/scenarios.example.yaml config/scenarios.yaml   # отредактировать
./docker/policy.sh config/scenarios.yaml
```

Подписывает кодовую книгу демо-корневым ключом и публикует её с номером версии на
единицу выше текущего. События с `until_cancelled: true` действуют до отбоя: в панели
они в блоке «Действующие события», а исполнитель, вошедший позже, получает их сразу.
Почему список в подписанной политике, а не в `.env`, — ADR 0010.

### Новый человек и отзыв ключа

```bash
./docker/person.sh add x-104 "Новиков П. С." fire-wardens     # исполнитель, пароль demo
ROLE=duty_officer ./docker/person.sh add p-004 "Орлова Е. В."
./docker/person.sh show                                       # справочник ключей
./docker/person.sh revoke x-104 "утерян телефон"              # все подписи недействительны
./docker/person.sh retire x-104                               # уволился: прежние в силе
```

`add` создаёт ключ «устройства» в томе clients, заводит контакт, подписывает
следующую версию справочника демо-корневым ключом и публикует её — после этого
человек входит на страницу исполнителя. `revoke` отзывает ключом отзыва дежурной
смены, без корневого ключа, за пару секунд; при первом вызове этот ключ создаётся в
томе demo-keys и вносится в справочник. `retire` публикует новую версию справочника.
Оба снимают контакт: следующий же запрос с этим ключом получает 403. Как
то же делается в боевом контуре, где корневой ключ не бывает в сети, —
docs/02-trust-and-approval.md §4.

### Исполнитель с телефона

Страница исполнителя: **http://127.0.0.1:7072** (порт — `ALERTING_MOBILE_PORT`), вход
`x-101`, `x-102` или `x-103`, пароль `demo`. Чтобы открыть её с телефона в той же сети,
поставьте `ALERTING_MOBILE_BIND=0.0.0.0` в `docker/.env`, перезапустите `./docker/up.sh`
и откройте `http://<адрес-сервера>:7072`. Подробнее — §9.

Ниже — те же шаги по отдельности и что за ними стоит.

## 1. Сборка

```bash
git clone https://github.com/pavel-yamal/alerting.git && cd alerting
cp docker/.env.example docker/.env
docker compose --env-file docker/.env build
```

За корпоративным TLS-прокси pip не доверяет его сертификату. Тогда:

```bash
docker build --secret id=ca,src=/path/corp-ca.crt -t alerting:local .
```

CA передаётся секретом сборки и в образ не попадает.

## 2. Организация (демо)

```bash
docker compose --env-file docker/.env --profile init run --rm org-init
```

Поднимает базу, генерирует пароли, создаёт демо-организацию и кладёт ключ подписи
голов аудита туда, где его ждёт сервер. В выводе — `ORG ROOT PUBLIC KEY`. Впишите
его в `docker/.env`:

```
ALERTING_ROOT_PUBKEY=<ключ из вывода>
```

**`org-init` стирает схему базы.** Повторный запуск — это новая организация с
новым корневым ключом, а старые клиенты перестают ей доверять. И он пишет корневой
**закрытый** ключ в том `alerting_demo-keys`: на боевом сервере его не запускают
вовсе (см. §5).

## 3. Запуск

```bash
docker compose --env-file docker/.env up -d --wait
curl -s http://127.0.0.1:7070/v1/readyz        # {"ready":true, ...}
docker compose --env-file docker/.env logs server | head
```

В первой строке журнала должно быть `audit heads : signed`, а не `UNSIGNED`.

Порядок обеспечивает compose: `secrets-init` → `db` → `migrate` (ролью владельца,
одноразово) → `server` (ролью приложения). Сервер не стартует, если миграции не
прошли.

## 4. Проверка учебным приказом

```bash
R="docker compose --env-file docker/.env --profile cli run --rm cli"
S="--server http://server:8080 --passphrase demo"
H=/var/lib/alerting/clients

$R alerting-approver propose TEST.PING --drill --severity info \
    --groups fire-wardens --text "проверка" --person p-001 --home $H/p-001 $S
$R alerting-approver sign <id> --yes --person p-001 --home $H/p-001 $S
$R alerting-approver status <id> --person p-001 --home $H/p-001 $S

$R alerting-executor sync          --person x-102 --home $H/x-102 $S
$R alerting-executor verify <id>   --person x-102 --home $H/x-102 $S   # ПОДЛИННЫЙ приказ

$R alerting-auditor verify --person p-001 --home $H/p-001 $S           # chain intact
```

У демо-людей ключи уже выданы. **Не запускайте `alerting-executor enroll`** для
них: он создаст новый ключ устройства, которого нет в справочнике, и человек получит
`403`.

## 5. Секреты

Через окружение не передаётся ни один. `secrets-init` генерирует пароли один раз и
раскладывает по трём томам, каждый файл `0400` и принадлежит тому, кто его читает:

| Том | Что | Кто читает |
|---|---|---|
| `alerting_db-secrets` | пароли ролей | postgres, при инициализации |
| `alerting_owner-secrets` | DSN владельца | только `migrate` и `org-init` |
| `alerting_app-secrets` | DSN приложения, ключ подписи голов | только `server` |

Сервер не видит DSN владельца, поэтому не может переписать журнал аудита.

**Боевой узел:** бандлы организации готовятся на машине без сети. На сервер
кладётся только ключ подписи голов:

```bash
docker run --rm -v alerting_app-secrets:/s -v "$PWD/server-key:/k:ro" busybox:1.36 \
    sh -c 'cp /k /s/server-key && chown 10001:10001 /s/server-key && chmod 0400 /s/server-key'
docker volume rm alerting_demo-keys     # если на этой машине когда-то был org-init
```

## 6. Эксплуатация

```bash
docker compose --env-file docker/.env ps
docker compose --env-file docker/.env logs -f server

# обновление: миграции применятся сами перед стартом сервера
git pull && docker compose --env-file docker/.env up -d --build --wait

# резервная копия базы
docker compose --env-file docker/.env exec -T db \
    pg_dump -U postgres -Fc alerting > alerting-$(date +%F).dump
```

Головы аудита лежат в томе `alerting_heads`. Их смысл в том, чтобы быть **вне**
базы: копируйте их на хост аудитора, иначе подделку журнала нечем обнаружить.

## 7. Чего здесь нет

- *(Было ограничение, теперь снято.)* Соединение исполнителя живёт в памяти того
  процесса, который его принял, а рассылку выполняет другой. Процессы передают приказ
  друг другу через PostgreSQL (`ws_presence`, `ws_relay`, `LISTEN/NOTIFY`), и `ws:sent`
  записывается только по подтверждению процесса, державшего сокет. Поэтому стенд снова
  работает в двух процессах. Подробно — `docs/04-channels.md`, раздел «Доставка между
  процессами».

- **Резерва базы.** Один PostgreSQL. Отказ машины — простой до восстановления
  из копии. Резерв и измеренное переключение есть только в systemd-контуре
  ([10-failover.md](10-failover.md)).
- **Реальных каналов.** push, SMS, голос, сирена — заглушки; поэтому в
  `.env.example` стоит `ALERTING_ALLOW_STUB_CHANNELS=1`. Доставляет только приложение
  (WebSocket).
- **TLS.** Его даёт nginx на хосте.

## 8. Панель дежурного: как устроена

Где лежит ключ человека — главное, что нужно знать о панели. Решение — ADR 0012.

**Ключ на устройстве.** Ключ создаётся в браузере человека (iPhone, iPad, Android,
рабочее место), хранится там зашифрованным его паролем и не покидает устройство.

- **Вход.** Браузер открывает ключ паролем и подписывает *доверенность на сеанс*:
  «запросы, подписанные этим сеансовым ключом, — мои, до такого-то времени» (не
  больше 12 часов; открытая страница сама продлевает её заранее). Сеансовый ключ
  создаёт панель; им она подписывает HTTP-запросы.
  Сервер проверяет доверенность на каждом запросе по текущему справочнику, поэтому
  отзыв ключа устройства обрывает все его сеансы сразу.
- **Подпись приказа.** Экран подписи строится в браузере из самого приказа — того же
  объекта, который подписывается. Подпись ставит ключ устройства, панель лишь
  проверяет её и передаёт серверу. Доверенность на сеанс приказы не подписывает:
  захватив панель, можно смотреть и создавать предложения, но не поставить чужую
  подпись.
- **Что нужно.** https:// (или localhost) и современный браузер: Safari 17+, Chrome,
  Firefox, Edge. На iPhone/iPad панель стоит добавить на экран «Домой», иначе Safari
  может стереть данные сайта, если его долго не открывать. Каждое устройство — свой
  ключ; потерянное отзывается отдельно (`person.sh revoke`).
- **Перезагрузка страницы закрывает ключ** — нужно войти снова.

**Демо-ключи на сервере** (`ALERTING_PANEL_DEMO_KEYS=1`). Панель расшифровывает ключ
из тома clients паролем. Тогда пароль — единственная защита, а тот, кто управляет
сервером, может подписывать за людей. Для реальной работы — `ALERTING_PANEL_DEMO_KEYS=0`.

Общее для обоих входов:

- **Подписывается только просмотренное.** При нажатии «Подписать» приказ берётся
  заново, его отпечаток пересчитывается и сравнивается с показанным. Изменился —
  подписи нет, человек смотрит заново.
- Поле, которое панель не умеет показать, блокирует подпись.
- Исполнителям вход закрыт: их ключи подписывают расписки, а не приказы.
- Сессия не истекает: она длится, пока человек не выйдет, его ключ не отзовут или
  её не завершит администратор (ниже, ADR 0014).
- Скрипты страницы — только с её собственного адреса (Content-Security-Policy), без
  встроенного кода: внедрённый скрипт мог бы попросить открытый ключ подписать.
- Запросы, меняющие состояние, требуют служебного заголовка.

**Публикация через обратный прокси — одним доменом.**
`deploy/nginx/alerting-one-domain.conf` вешает всё на один адрес:

| Путь | Куда | Кто ходит |
|---|---|---|
| `/`, `/api/*`, `/privacy` | панель, `127.0.0.1:7071` | браузер дежурного и ЛПР, приложение ЛПР |
| `/v1/*` | API сервера, `127.0.0.1:7070` | консоль, страница исполнителя, аудитор |

Пути не пересекаются: панель отвечает только на `/`, `/api/*`, `/privacy` и свои
скрипты, сервер — только на `/v1/*`. Приложению ЛПР нужен **только этот адрес**: оно
говорит с панелью, а панель с сервером — внутри, по `http://server:8080`, мимо прокси.
В конфиге уже ограничена частота `/api/device/begin` и `/api/login`, а `/healthz`,
`/v1/readyz` и `/v1/metricsz` закрыты снаружи. Демо-вход (`ALERTING_PANEL_DEMO_KEYS`)
наружу не выпускать.

```bash
sudo cp deploy/nginx/alerting-one-domain.conf deploy/nginx/alerting-tls-params.conf /etc/nginx/conf.d/
sudo sed -i 's/alert\.example\.org/alert.yamal-media.ru/' /etc/nginx/conf.d/alerting-one-domain.conf
# пути к сертификату — строки с ADJUST
sudo nginx -t && sudo systemctl reload nginx
curl https://alert.yamal-media.ru/api/config      # {"org_id": ..., "device_login": true, ...}
```

Нужен nginx 1.25+ (`http2 on;`); на более старом замените эту строку на
`listen 443 ssl http2;`.

**Чего здесь нет.** Списка всех предложений на сервере нет (у сервера нет такого
запроса), поэтому «Ожидают подписи» показывает предложения, созданные или открытые
через эту панель. Предложение из консоли открывается по ID. Ключ хранится программно
(песочница браузера); аппаратный ключ (passkey, Face ID) — следующий шаг.

## 9. Страница исполнителя: что она показывает и чего не обещает

Сценарий для показа: исполнитель держит страницу открытой на телефоне, двое ЛПР
подписывают приказ в панели, на телефоне со звуком и вибрацией появляется
«✓ ПОДЛИННЫЙ ПРИКАЗ», кто подписал, сценарий и пояснение, и три слова, которые должны
быть в SMS по этому приказу. Исполнитель нажимает «Принял» — в панели дежурного
«Подтвердили: 1 из 2». Есть «Выдвинулся», «Выполнил» и «Не могу» (с причиной).

Как это устроено. `alerting-mobile` — клиент исполнителя, как `alerting-executor
listen`: держит ключ устройства, слушает поток приказов и решает, подлинный ли приказ,
тем же кодом и по тому же закреплённому корневому ключу. Приказ, который не прошёл
проверку, показывается как «ОТКЛОНЕНО — НЕ ВЫПОЛНЯТЬ» с причиной, и подтвердить его
нельзя. Получив подлинный приказ, клиент сам отправляет расписку «получено
устройством»; подтверждение человека — отдельное нажатие.

**Чего эта страница не обещает — и сама об этом пишет:**

- **Проверка идёт не в телефоне**, а в процессе `alerting-mobile` на стенде, рядом с
  ключами демо-исполнителей. Это демонстрация потока, а не граница доверия. Нативное
  приложение переносит ровно эту логику в телефон, а ключ — в Keystore/Secure Enclave.
- **Закрытая страница или спящий телефон приказ не получат.** Браузер не держит
  соединение в фоне; для этого нужны push-уведомления (FCM/APNs) и приложение.
- С телефона в той же сети страница идёт по HTTP, без шифрования. Уведомления
  браузера и установка на главный экран работают только по HTTPS или на localhost.
- Сессия исполнителя не истекает: она длится, пока человек не выйдет, его ключ не
  отзовут или её не завершит администратор.

**Завершить сессию** (панель или страница исполнителя), не отзывая ключ:

```
docker compose exec panel  alerting-panel  sessions            # кто вошёл
docker compose exec panel  alerting-panel  end-session p-003   # или --all
docker compose exec mobile alerting-mobile sessions
docker compose exec mobile alerting-mobile end-session x-101
```

Команда читает токен, который процесс при запуске пишет в `admin.token` своего
каталога состояния, и без него ничего не делает. Отзыв ключа (`person.sh revoke`)
закрывает все сессии человека сам, в течение 30 секунд.

## 10. RSS-лента оповещений

`GET /v1/feed.rss` — публичная лента, без входа и подписи запроса: боевые оповещения
и отбои по ним, новые сверху (`?limit=` — до 200, по умолчанию 50). В каждой записи:
событие и уровень в заголовке, текст приказа и инструкция из кодовой книги в
описании, время рассылки, код сценария, идентификатор приказа.

В ленту **не попадают**: учения и технические проверки (canary), список получателей, кто подписал и кто подтвердил. Текст приказа публикуется как есть —
не пишите в него персональные данные.

Лента — представление уже разосланных приказов, а не канал доставки: её читают
периодическим опросом, как любую RSS. На стенде: `http://127.0.0.1:7070/v1/feed.rss`.
