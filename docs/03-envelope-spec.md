# Нормативный формат приказа

## 1. Канонизация — RFC 8785 (JCS)

Подпись берётся над `ДОМЕН || JCS(payload)`.

Почему JCS, а не детерминированный CBOR: **подписанные байты остаются читаемыми
человеком**. Аудитор, инженер поддержки и эксперт в суде видят в журнале ровно тот
приказ, который был одобрен, без какого-либо инструмента. Для системы, весь смысл
которой в доказуемости авторства, это перевешивает компактность CBOR.

Острые углы JCS сняты не изменением формата, а отказом канонизировать опасные случаи
(`src/alerting/core/canonical.py`):

| Ограничение | Почему |
|---|---|
| **Никаких float** | Форматирование чисел в ECMAScript — главный источник расхождений между реализациями JCS. Все числа здесь — счётчики и Unix-секунды |
| **Никаких `null`** | `{"a": null}` и `{}` — разные подписанные байты. Отсутствует значит отсутствует: модели сериализуются с `exclude_none` |
| **NFC везде** | Две визуально одинаковые строки с разной нормализацией дали бы две разные подписи «одного» приказа |
| **Целые в пределах 2⁵³−1** | Дальше читатель на ECMAScript молча теряет точность и хэшировал бы другие байты |
| Ключи сортируются по **кодовым единицам UTF-16** | Требование RFC; отличается от сортировки Python по кодовым точкам для астральных символов |

## 2. Нагрузка

```jsonc
{
  "v": 1,
  "type": "order",                  // order | cancel
  "order_id": "4f2c…",              // UUIDv4
  "org_id": "acme",
  "stream_id": "primary",           // независимые пространства seq (напр. по площадкам)
  "seq": 1247,                      // монотонный внутри (org_id, stream_id)
  "nonce": "b64url-16b",
  "issued_at": 1758300000,          // int, Unix-секунды UTC
  "not_valid_after": 1758300900,    // строго больше issued_at
  "severity": "critical",           // info | warning | critical | catastrophic
  "drill": false,                   // ОБЯЗАТЕЛЬНОЕ, без умолчания
  "scenario": "EVAC.BUILDING",      // код из кодовой книги — единственное действенное поле
  "action": "START",                // START | STOP | HOLD
  "audience": {"sites": ["hq"], "groups": ["fire-wardens"], "persons": []},
  "text": "Задымление, 3 этаж",     // справочное
  "requires_ack": true,
  "ack_deadline_s": 120,
  "policy_id": "demo-policy-2026-01"
  // "cancels": "<order_id>"        // ТОЛЬКО для type=cancel; иначе ключ отсутствует
}
```

Три правила, которые являются мерами защиты, а не стилем
(`src/alerting/core/envelope.py`):

- **`extra="forbid"`** — неизвестное поле это отказ, а не повод молча его отбросить.
  Отбросив, мы получили бы: проверенные байты ≠ разобранные байты.
- **Строгие скаляры** — `"seq": "1247"` не должно превратиться в `1247`. Основная
  гарантия здесь — сверка канонических байт в `verify_envelope`, а строгие типы дают
  отказ раньше и с понятным сообщением.
- **`drill` без значения по умолчанию.** Забытый флаг обязан быть невалидным
  конвертом, а не молча «боевым» приказом. Это поле, которое с наибольшей
  вероятностью кого-то покалечит.

**`cancels` отсутствует у обычного приказа, а не равен `null`** — прямое следствие
запрета `null` в канонизации.

## 3. Подписи

```jsonc
{
  "payload": { /* ровно как выше */ },
  "signatures": [
    {"key_id": "ed25519:AbC…", "alg": "Ed25519", "sig": "b64url-64b"}
  ]
}
```

**В записи подписи намеренно нет `signed_at`.** Всё, что вне подписанной нагрузки,
подделываемо, а подделываемая отметка времени, которая *выглядит* авторитетной, хуже,
чем её отсутствие. Свидетельство времени берётся из цепочки аудита (наблюдение
сервера) и из `issued_at` + `max_signature_spread_s`.

### Доменное разделение

Все различны, все с завершающим NUL (`src/alerting/core/signing.py`):
`alerting.order.v1`, `alerting.ack.v1`, `alerting.directory.v1`, `alerting.policy.v1`,
`alerting.audit-head.v1`, `alerting.device-auth.v1`, и метка HMAC `alerting.wake.v1`.

Без разделения тело расписки, подобранное так, чтобы разбираться и как нагрузка
приказа, несло бы валидное «одобрение».

## 4. Защита от повтора — скользящее окно

Очевидная схема «отбросить любой `seq` не больше виденного» здесь неверна, причём в
опасную сторону. Два приказа, отправленных с разницей в секунды, могут прийти не по
порядку через WebSocket и push. При голом счётчике второй пришедший молча теряется — и
противник, способный слегка повлиять на порядок доставки, получает примитив подавления
бесплатно.

Поэтому окно в стиле IPsec (`src/alerting/core/replay.py`):

| Ситуация | Вердикт | Действие |
|---|---|---|
| `seq` больше максимума | `FRESH` | принять, сдвинуть окно |
| В окне, бит не взведён | `FRESH` | принять, взвести бит |
| В окне, бит взведён | `DUPLICATE` | **отказ** — это настоящий повтор |
| Ниже окна | `OUT_OF_WINDOW` | **предупреждение**, решает человек |

Плюс дедупликация по `order_id` и проверка `not_valid_after` с допуском ±120 с.

`verify_envelope` **не изменяет** окно: фиксацию делает вызывающая сторона после
решения действовать, поэтому отвергнутый конверт не может отравить окно.

## 5. Отбой

Отбой — полноценный конверт с `type: "cancel"`, `cancels: <order_id>`, собственными
`order_id`, `seq`, `nonce`, TTL и **тем же значением `drill`, что у цели**. Учебным
конвертом нельзя отменить боевой приказ и наоборот.

Кворум отбоя ниже кворума запуска — обоснование и четыре компенсирующих барьера в
[adr/0003-cancel-quorum.md](adr/0003-cancel-quorum.md).

## 6. Расписка

```jsonc
{"v": 1, "type": "ack", "order_id": "4f2c…", "org_id": "acme",
 "person_id": "x-101", "device_key_id": "ed25519:…",
 "status": "acknowledged",        // received|acknowledged|en_route|completed|cannot_comply
 "at": 1758300042, "nonce": "…",
 "order_digest": "b64url-sha256-от-JCS(нагрузки приказа)"
 // "reason": "…"                 // обязателен при cannot_comply
}
```

`order_digest` — несущее поле: оно доказывает, **какой именно текст приказа
исполнитель видел перед собой**. Без него взломанный сервер мог бы позже утверждать,
что приказ был мягче, чем тот, по которому действовали.

`received` устройство шлёт само; всё остальное — только по нажатию человека.

## 7. Порядок проверки

`verify_envelope` выполняет десять шагов, собирая все причины, а не останавливаясь на
первой:

1. схема, версия, **совпадение канонических байт с полученными**;
2. `org_id`;
3. свежесть справочника (только предупреждение);
4. привязка к `policy_id` и срок политики;
5. каждая подпись: ключ известен, не отозван, подпись валидна;
6. кворум: `m`, `distinct_persons`, `min_from_role`;
7. окно повторов и дедупликация по `order_id`;
8. TTL и перекос часов;
9. семантика `drill`, сверка с отменяемым приказом;
10. сценарий в кодовой книге и границы важности.
