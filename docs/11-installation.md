# Установка контура с нуля

`docs/09-deployment.md` — справочник: что где лежит и почему так. Этот документ —
процедура: с пустых машин до работающего контура, по шагам.

Они разделены намеренно. Документ, в котором «почему так» перемешано с «делай так»,
плох в обеих ролях: его не читают перед началом и в него не смотрят посреди работы.

**Порядок шагов значим.** Он выбран так, что каждый следующий проверяется предыдущим,
а не тем, что «вроде поднялось».

---

## 0. Что должно быть до начала

| | |
|---|---|
| Пять машин | Ubuntu/Debian, systemd, root или sudo по SSH |
| Сеть | машины видят друг друга; наружу смотрит только прокси |
| Выход в интернет | для `apt` и PyPI. Изолированный контур — см. §9 |
| Сертификат TLS | корпоративный, либо `make-ca.sh` для стенда |
| Корневой ключ организации | **публичная** половина; см. §5 про то, откуда берётся закрытая |

Роли машин:

```
proxy    nginx, TLS, allow-списки          — единственная, до которой достают люди
app-1    alerting.service, --workers 2
app-2    alerting.service, --workers 2
db-1     PostgreSQL, основная
db-2     PostgreSQL, резерв
```

## 1. Инвентарь

Один файл, из которого берутся все адреса. Все конфигурации собираются из него, и
это единственное место, где адреса нужно вписать руками.

```bash
cp deploy/inventory.example.env deploy/inventory.env
$EDITOR deploy/inventory.env
```

До него `10.0.10.11` был зашит в юнит, `10.0.10.0/24` — в nginx и в правила
firewall, `10.0.20.7` — ещё в одном месте. Шесть файлов, которые обязаны
согласовываться, и ни одного места, где это видно. Расхождение при этом не падает:
firewall режет не тех, nginx ходит не туда, и обе машины выглядят настроенными.

`ALERTING_CONTOUR` — `staging` или `production`. Значение не косметическое:
установщик по нему решает, ставить ли заглушки каналов, а `make-ca.sh` отказывается
выпускать самоподписанный сертификат для боевого контура.

## 2. Общая подготовка — на всех пяти машинах

```bash
# на app-1 и app-2
./deploy/install/common.sh app
# на db-1 и db-2
./deploy/install/common.sh db
# на proxy
./deploy/install/common.sh proxy
```

Создаёт пользователя `alerting`, каталоги с правильными правами, ставит chrony и
раскладывает правила firewall — **но не применяет их**. Применение обрывает текущие
соединения, включая ваш собственный SSH, если `ALERTING_ADMIN_NET` указан неверно.
Сверьте адрес и примените сами:

```bash
systemctl enable --now nftables && nft -f /etc/nftables.conf
```

Часы — не формальность. Окно рукопожатия устройства 60 с, допуск перекоса приказа
±120 с, и потеря синхронизации это **молчаливый полный отказ**: валидные клиенты
начинают получать отказ, а узел выглядит здоровым. Юнит не стартует, пока
`chronyc waitsync` не пройдёт.

## 3. Основная база — db-1

```bash
OWNER_PASSWORD=… APP_PASSWORD=… REPL_PASSWORD=… ./deploy/install/db-primary.sh
```

Три роли, и разделение между ними — не формальность. `alerting_app` имеет по
`audit_log` только `SELECT` и `INSERT`: **полностью скомпрометированный процесс
сервера не может переписать историю.** Не «будет остановлен триггером» — не имеет
права попробовать. Никогда не выдавайте серверу DSN владельца; если оба юнита читают
один файл, разделение исчезает, и об этом ничто не сообщит.

Пароли приходят снаружи и не печатаются в лог: те же значения нужны на узлах
приложения, а лог установки читают и пересылают.

**Проверить до перехода дальше** — с app-1, а не с самой базы:

```bash
psql "postgres://alerting_app:…@<db-1>:5432/alerting" -tAc "select current_user"
```

Не прошло — смотрите `pg_hba.conf` на db-1 и правило на 5432 в firewall app-1.
Раньше этого правила не было вовсе, и узел не дошёл бы до базы.

## 4. Узлы приложения — app-1 и app-2

```bash
NODE=app1 ./deploy/install/app-node.sh    # на app-1
NODE=app2 ./deploy/install/app-node.sh    # на app-2
```

Раскладывает релиз в `/opt/alerting/releases/<версия>/`, собирает venv, ставит юниты
с подставленным адресом привязки. **Сервис не запускает** — это отдельное решение
человека.

Дальше вручную, и это не лень автоматизации:

1. **Секреты** — `/etc/alerting/credentials/{dsn-app,dsn-owner,server-key}`, режим
   `0400 root:root`. Сервер отказывается использовать файл, доступный группе или
   остальным. Подробности — `deploy/env/credentials.README.md`.
2. **`ALERTING_ROOT_PUBKEY`** в `/etc/alerting/alerting.env`. **Сверьте его вне
   канала** с тем, что держат хранители: подменённый корневой ключ пропускает
   поддельный справочник, и проверка этого не заметит — она будет проходить.
3. **Проверка конфигурации без запуска:**
   ```bash
   /opt/alerting/current/venv/bin/alerting-server --check
   ```

## 5. Организация

Бандлы готовятся **не на узле**. На узел едут только опубликованные бандлы и
публичный корневой ключ.

Для стенда — фиктивная организация, с машины оператора:

```bash
ALERTING_DSN="postgres://alerting_owner:…@<db-1>:5432/alerting" \
    python scripts/org_init.py --i-understand-this-is-a-demo
```

Флаг обязателен и назван честно: скрипт пишет **корневой закрытый ключ организации
на локальный диск**. Это якорь доверия всей системы — кто им владеет, подписывает
справочник и политику, то есть назначает, чьи подписи считаются приказом.

**Для боевого контура этого скрипта недостаточно, и он сам об этом говорит**: при
`ALERTING_ENV=production` он отказывается работать. Боевой корневой ключ рождается на
машине без сети и живёт на двух зашифрованных носителях у двух хранителей
(`docs/02-trust-and-approval.md`). Стенд проходит ту же последовательность шагов
ровно затем, чтобы отрепетировать правильный порядок, а не удобный.

## 6. Запуск

```bash
systemctl enable --now alerting alerting-artifacts-backup.timer   # на обоих узлах
```

`alerting.service` требует `alerting-migrate.service`, поэтому миграции применятся
первыми, а узел не поднимется, если они не прошли. Два узла, стартующие
одновременно, безопасны: миграции сериализованы advisory-блокировкой, и второй
найдёт, что делать нечего.

## 7. Прокси

```bash
./deploy/install/make-ca.sh /path/к/ca          # только для стенда
CERT_DIR=/path/к/ca ./deploy/install/proxy.sh   # на proxy
```

`proxy.sh` делает `nginx -t` — **первую проверку этого конфига за всю его жизнь**:
он писался в контейнере, где nginx не установлен, и до сих пор не проверялся ничем.
Он же убирает дефолтный сайт Debian, который иначе отвечает «Welcome to nginx» на всё,
что не совпало с `server_name`.

## 8. Резерв базы — db-2

```bash
REPL_PASSWORD=… ./deploy/install/db-standby.sh
```

Ставится последним намеренно: резерв снимает базовую копию с работающей основной, и
копировать пустую базу до того, как в ней появились схема и организация, смысла нет.

Резерв на выделенной машине стоит на обычном 5432. Порт 5433 нужен был только тогда,
когда обе базы делили один хост.

## 9. Приёмка

Не «поднялось», а «делает то, что обещано в документах». Каждый пункт — команда.

| # | Что проверяется | Чем |
|---|---|---|
| 1 | Юниты валидны | `systemd-analyze verify /etc/systemd/system/alerting*.service` |
| 2 | Секреты доехали | узел стартовал; в журнале `audit heads : signed`, а не `UNSIGNED` |
| 3 | Сервер работает ролью приложения и не может переписать журнал | три команды из `credentials.README.md`, раздел «Проверка» |
| 4 | Ключ не утёк в окружение | `tr '\0' '\n' < /proc/$(pgrep -f alerting-server)/environ \| grep -i 'KEY='` — пусто |
| 5 | Готовность зелёная на обоих | `curl http://<app-N>:8080/v1/readyz` |
| 6 | Лидер ровно один | `alerting_escalation_leader` = 1 суммарно по двум узлам |
| 7 | Приказ проходит весь контур | подписать и разослать учебный приказ снаружи, через nginx, настоящим CLI с персональным ключом |
| 8 | Канарейка доходит | `alerting_canary_ok` = 1, `alerting_canary_age_seconds` меньше интервала |
| 9 | Метрики не текут | в ответе `/v1/metricsz` нет ни одного `person_id`, имени и телефона |
| 10 | Отставание репликации измеряется | `alerting_replication_standbys` = 1 **и** `alerting_replication_lag_unknown` = 0 |
| 11 | Узел на базе в recovery отвечает 503 | направить узел в db-2 до промоушена: `writable: false`, а не падение |
| 12 | **Переключение, замеренное на настоящей сети** | `failover-drill.sh` с `PRIMARY_SSH`/`STANDBY_SSH` |
| 13 | Потеря хвоста обнаруживается | `lost-tail-check.sh` между хостами |
| 14 | Бэкап и восстановление | таймеры отработали на db-1 и на обоих узлах; `alerting-restore-drill.sh` |
| 15 | Узел переживает перезагрузку | `reboot` на app-1: поднялся сам, лидерство перешло и вернулось |

Пункты 12–14 — те, ради которых стенд и существует: их нельзя отрепетировать на
бумаге. Числа из `docs/10-failover.md` §1 получены на loopback, и там прямо сказано,
что на реальной сети они не применяются. Результат пункта 12 дописывается туда рядом.

## 10. Изолированный контур

Установщик ставит пакеты `apt` и зависимости с PyPI. Если выхода наружу нет:

- внутреннее зеркало — задать `PIP_INDEX_URL` и источники apt до запуска;
- совсем без сети — собрать venv на машине той же архитектуры и версии Python,
  перенести `/opt/alerting/releases/<версия>` целиком, а из установщика выполнить
  только шаги конфигурации.

Проверено это не было, и написано здесь как направление, а не как процедура.

## 11. Чего эта установка не даёт

Сказано здесь, а не в конце приёмки, потому что от этого зависит, можно ли называть
контур боевым.

**Четыре канала из пяти ничего не отправляют.** `push`, `sms`, `voice` и сирена
возвращают статус `stub`. Узел отказывается стартовать с такой лестницей эскалации,
пока ему явно не передадут `ALERTING_ALLOW_STUB_CHANNELS=1`, и установщик ставит этот
флаг **только** при `ALERTING_CONTOUR=staging`. Следствие для эксплуатации:
оповещение доходит только до тех, у кого открыто приложение исполнителя, а
напечатанный резервный порядок (`docs/06-runbook.md` §8) — основной способ
оповещения, а не запасной.

**Переход в боевой контур требует, помимо приёмки:**

1. подключённых настоящих провайдеров каналов;
2. корневого ключа, рождённого на машине без сети и находящегося у хранителей;
3. пройденной проверки по персональным данным (`docs/08-personal-data.md`) — в
   реестре появятся настоящие телефоны;
4. отработанного с секундомером отзыва: `docs/06-runbook.md` называет целью
   60 секунд, и это репетируется, а не предполагается.
