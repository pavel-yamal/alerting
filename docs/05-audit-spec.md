# Аудит

## 1. Цепочка

Журнал только на добавление. Каждая запись содержит хэш предыдущей, поэтому правка,
перестановка или удаление в любом месте обесценивают всё, что идёт дальше.

```
entry      = {"idx", "ts", "prev", "event", "data"}
entry_hash = sha256(b"alerting.audit.v1\x00" + JCS(entry))
```

Нулевая запись ссылается на 32 нулевых байта.

Подписи и тела расписок лежат в `data` дословно — цепочка самодостаточна как
доказательство, а не ссылается на изменяемые строки.

### События

`proposal.created`, `proposal.signed`, `proposal.rejected`, `quorum.met`, `order.dispatched`,
`channel.attempted`, `channel.receipt`, `ack.received`, `ack.rejected`,
`cancel.issued`, `escalation.rung_fired`, `directory.published`, `policy.published`,
`key.enrolled`, `key.revoked`, `drill.window.opened`, `manual.backfill`,
`audit.head_published`.

## 2. Что цепочка ловит, а что нет

Сказано прямо, потому что в разборе инцидента эта разница важна.

| Воздействие | Обнаруживается | Чем |
|---|---|---|
| Правка записи в середине | да, с указанием номера | ссылкой `prev` следующей записи |
| Перестановка | да | разрывом в нумерации |
| Удаление в середине | да | тем же разрывом |
| **Правка последней записи** | **нет, самой цепочкой** | только опубликованной головой |
| **Обрезка хвоста** | **нет, самой цепочкой** | только опубликованной головой |

У последней записи нет следующего звена, которое могло бы ей противоречить. Именно для
этого существуют головы. `auditor verify --ignore-heads` честно печатает, что в этом
режиме переписанный хвост не обнаруживается.

## 3. Головы

Каждые 100 записей и раз в час сервер подписывает `{idx, head, ts}` своим ключом
(домен `alerting.audit-head.v1`) и публикует.

Ключ задаётся переменной `ALERTING_SERVER_KEY` (base64url, Ed25519); `make org-init`
генерирует его и печатает публичную половину для аудитора. **Без ключа голова
публикуется с пустой подписью** — проверить её невозможно, и тот, кто переписывает базу,
подменит головы вместе с цепочкой. Сервер в этом случае пишет предупреждение при старте,
но не отказывается работать: оповещать важнее, чем иметь идеальный журнал.

В прототипе — файл в `var/heads/`. В эксплуатации — письмо аудиторам, сообщение во
внутренний канал, при желании метка времени RFC 3161. Смысл один: **как только голова
лежит в трёх чужих почтовых ящиках, переписанная история до неё уже не дотянется.**

## 4. Триггеры базы против настоящей защиты

В таблице `audit_log` стоят триггеры, запрещающие `UPDATE` и `DELETE`, а в `repo.py`
нет соответствующих методов. Это защита **от неосторожного администратора**, не от
того, у кого есть root: триггер можно снять. Тест
`test_verify_fails_at_the_right_index_after_a_direct_edit` именно это и делает —
снимает триггер, правит строку и проверяет, что цепочка ловит правку.

Настоящая защита — цепочка и внешне опубликованные головы.

## 5. Персональные данные — жёсткое ограничение

**В записях цепочки не должно быть персональных данных.** Цепочка принципиально
неудаляема, и это сталкивается лоб в лоб с обязанностью удалить данные по требованию.

Поэтому:

- в `data` идут только псевдонимы `person_id`, роли, идентификаторы ключей;
- ФИО, телефоны и прочее живут в отдельной таблице `contacts`, которую можно удалить
  (`Repo.forget_contact`);
- удаление контакта **не ломает** проверяемость цепочки — это отдельный тест.

`AuditService.append` дополнительно вычищает `None`, чтобы одно забытое необязательное
поле не отправило запись в спул посреди инцидента.

## 6. Журнал никогда не блокирует оповещение

Если запись в аудит не удалась, **рассылка всё равно идёт**: запись уходит в
`var/spool/audit-spool.jsonl`, дежурный получает громкую ошибку.

Система, отказывающаяся предупредить людей потому, что не смогла записать строку в
журнал, выбрала не тот отказ. Тест:
`test_an_audit_failure_never_blocks_the_alert`.

## 7. Работа аудитора

```bash
alerting-auditor pull   --server http://host:8080 --out chain.json
alerting-auditor verify --file chain.json
alerting-auditor heads  --server http://host:8080 --server-key <b64u>
alerting-auditor report --file chain.json --order-id <uuid>
```

Аудитор работает с выгрузкой, а не с базой. `--dsn` существует для оператора на узле;
проверяющий с доступом к боевой базе доверяет той самой машине, чью историю проверяет.

`report` восстанавливает хронологию по одному приказу и отдельно помечает **быстрые
циклы «запуск → отбой → запуск» короче десяти минут**: именно так выглядел бы
вынужденный или ошибочный отбой, и это повод посмотреть человеку.
