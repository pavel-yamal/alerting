# RSS-лента оповещений

`GET /v1/feed.rss` — RSS 2.0, UTF-8, `Content-Type: application/rss+xml`. Без входа и
без подписи запроса; кому лента видна, решает обратный прокси (§7). Код —
`src/alerting/server/api/feed.py`.

## 1. Что попадает в ленту

Лента — это **представление уже вышедших приказов**, собирается из базы при каждом
запросе. Приказ появляется в ней в момент, когда второй ЛПР поставил подпись и
сервер его принял. Предложения, которые ещё ждут подписи, в ленту не попадают.

| Запись | Когда есть в ленте |
|---|---|
| Оповещение (боевое) | всегда |
| Отбой по боевому оповещению | всегда |
| Учение и отбой учения | только при `ALERTING_DELIVERY=rss` (по умолчанию в Docker), заголовок начинается с «УЧЕНИЕ.» |
| Техническая проверка (canary) | никогда |

В ленте **нет**: кому адресован приказ, кто подписал, кто подтвердил. Это остаётся за
входом с подписью запроса: список получателей — персональные данные.

## 2. Откуда берутся тексты

У каждой записи три источника текста:

| Что | Откуда | Кто и как меняет |
|---|---|---|
| **Название события** (`description` сценария, например «Полная эвакуация здания») | кодовая книга `config/scenarios.yaml`, подписанная корневым ключом в составе политики | хранители корня: правка файла, подпись и публикация (`./docker/policy.sh config/scenarios.yaml` на стенде, docs/02-trust-and-approval.md §5 в боевом контуре) |
| **Инструкция людям** (`card` сценария, например «Выйти по ближайшему маршруту…») | там же | там же |
| **Пояснение** к конкретному приказу | поле «Пояснение» при создании предложения в панели или приложении ЛПР (`--text` в CLI); до 1000 знаков, необязательно | тот, кто создаёт предложение; подписывающие ЛПР видят его до подписи, после подписи оно не меняется |
| **Причина отбоя** | поле «Причина отбоя» при создании отбоя | тот, кто создаёт отбой |

Название и инструкцию сервер **не хранит у себя и не может подменить**: они берутся
из подписанной политики. Пояснение входит в подписанный приказ. Текст публикуется как
есть — **не пишите в него персональные данные**.

Если сценарий в политике переименовали после приказа, старые записи ленты покажут
новое название: лента собирается заново при каждом запросе.

## 3. Структура

### Канал

| Элемент | Значение |
|---|---|
| `title` | `<ALERTING_ORG_LABEL>: оповещения` |
| `link` | абсолютный адрес ленты: `ALERTING_PUBLIC_URL` + `/v1/feed.rss`; без настройки — из адреса запроса (§6) |
| `description` | «Оповещения и отбои; учения помечены «УЧЕНИЕ».» при `ALERTING_DELIVERY=rss`, иначе «Боевые оповещения и отбои. Учения в ленту не попадают.» |
| `language` | `ru` |
| `atom:link` | `rel="self"`, тот же адрес — ссылка ленты на саму себя, её ждут валидаторы и читалки |
| `lastBuildDate` | время выхода самой новой записи (RFC 822, GMT); нет, если лента пуста |

Пространства имён: `atom` = `http://www.w3.org/2005/Atom`, `alerting` =
`urn:x-alerting:rss:1` (элементы этой системы).

### Запись (`item`) об оповещении

| Элемент | Значение |
|---|---|
| `title` | `[УЧЕНИЕ. ]<название события>` |
| `description` | пояснение и инструкция через пустую строку; если пояснения нет — только инструкция |
| `category` | код сценария: `EVAC.BUILDING`, `SHELTER.IN.PLACE`, `MUSTER`, `STAND.BY`, `TEST.PING` или свой из кодовой книги |
| `pubDate` | время выхода приказа (после второй подписи), RFC 822, GMT |
| `guid` | идентификатор приказа (UUID), `isPermaLink="false"` |

### Запись об отбое

| Элемент | Значение |
|---|---|
| `title` | `[УЧЕНИЕ. ]ОТБОЙ: <название события, которое отменяется>` |
| `description` | причина отбоя; если не указана — «Оповещение отменено.» |
| `category` | код сценария отменяемого события |
| `pubDate` | время выхода отбоя |
| `guid` | идентификатор самого отбоя |
| `alerting:cancels` | `guid` оповещения, которое этот отбой отменяет |

Элемента `link` у записей нет. Уровня важности в записи нет: он определяется
сценарием.

### Порядок и объём

Новые сверху. По умолчанию 50 записей, `?limit=` — от 1 до 200. Отбой, ушедший за
пределы окна, своё событие уже закрыл у всех, кто читал ленту в это время.

## 4. Пример

```xml
<?xml version='1.0' encoding='utf-8'?>
<rss xmlns:alerting="urn:x-alerting:rss:1" xmlns:atom="http://www.w3.org/2005/Atom" version="2.0">
  <channel>
    <title>ACME: оповещения</title>
    <link>https://alert.example.org/v1/feed.rss</link>
    <description>Боевые оповещения и отбои. Учения в ленту не попадают.</description>
    <language>ru</language>
    <atom:link href="https://alert.example.org/v1/feed.rss" rel="self" type="application/rss+xml"/>
    <lastBuildDate>Tue, 14 Nov 2023 22:23:25 GMT</lastBuildDate>
    <item>
      <title>ОТБОЙ: Полная эвакуация здания</title>
      <description>Очаг ликвидирован, возвращаться можно</description>
      <category>EVAC.BUILDING</category>
      <pubDate>Tue, 14 Nov 2023 22:23:25 GMT</pubDate>
      <guid isPermaLink="false">d9ba548d-d496-4f97-9680-030c6c4909fe</guid>
      <alerting:cancels>0068cc6b-5452-46d3-835b-a177f5fc58ae</alerting:cancels>
    </item>
    <item>
      <title>Полная эвакуация здания</title>
      <description>Задымление, 3 этаж, корпус А

Выйти по ближайшему маршруту, пункт сбора по схеме на карточке. Вернуться только по отбою.</description>
      <category>EVAC.BUILDING</category>
      <pubDate>Tue, 14 Nov 2023 22:13:25 GMT</pubDate>
      <guid isPermaLink="false">0068cc6b-5452-46d3-835b-a177f5fc58ae</guid>
    </item>
  </channel>
</rss>
```

## 5. Как читать

- Опрашивать периодически, как любую RSS; лента не канал доставки и ничего не
  обещает о задержке.
- Новизну записи определять по `guid`.
- Действующие события: оповещение действует, пока не вышел отбой, у которого
  `alerting:cancels` равен его `guid` (все сценарии — «до отбоя»). Связь точная, даже
  если одновременно идут два события одного сценария. Читалки, не знающие элемента
  `alerting:cancels`, его просто пропускают и показывают запись как обычно (проверено
  на feedparser: `entry.alerting_cancels`).
- Текст экранирован как XML. Разметки в нём нет, переводы строк — обычные `\n`.

## 6. Адрес ленты (`ALERTING_PUBLIC_URL`)

Ссылки канала (`link`, `atom:link`) — абсолютный адрес ленты. Узел за nginx в
контейнере сам видит только `http://` и внутренний адрес, поэтому внешний адрес
задаётся явно: в `docker/.env` (или `/etc/alerting/alerting.env`)

```bash
ALERTING_PUBLIC_URL=https://alert.example.org
```

и `./docker/up.sh`. Без настройки ссылка строится из заголовка `Host`, который
передаёт nginx (`proxy_set_header Host $host`), со схемой, которую видит узел, —
обычно `http://`.

## 7. Доступ

Сервер отдаёт ленту без входа. В `deploy/nginx/alerting-one-domain.conf` она открыта
только внутренним сетям (`allow … / deny all`), снаружи — 403. Если перед этим nginx
стоит ещё один прокси, все запросы приходят с его адреса: фильтровать тогда на нём
либо включить `set_real_ip_from <его адрес>; real_ip_header X-Forwarded-For;`. На
стенде: `http://127.0.0.1:7070/v1/feed.rss`.
