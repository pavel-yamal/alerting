# Эксплуатация

## 1. Развёртывание

> **Это быстрый старт для проверяющего, а не инструкция по эксплуатации.**
> Он поднимает демо-организацию на одной машине.
> Реальное развёртывание — [09-deployment.md](09-deployment.md): systemd, TLS,
> обратный прокси, резервные копии, учебное восстановление, готовность и живость.

```bash
make setup
make db-up             # PostgreSQL: роли, база, миграции
make org-init          # демо-организация; печатает корневой публичный ключ и пути к секретам

ALERTING_ROOT_PUBKEY=<b64u> \
ALERTING_SERVER_KEY_FILE=var/server-key.SECRET \
ALERTING_ALLOW_STUB_CHANNELS=1 \
ALERTING_DSN="$ALERTING_DSN" make serve

# Общего ключа нет: каждый CLI подписывает свои запросы персональным ключом.
#   alerting-approver status <id> --person p-001 --home var/clients/p-001
```

В бою сервер подключается ролью `alerting_app`, у которой по журналу аудита есть
только `SELECT` и `INSERT`, а DSN приходит файлом через `LoadCredential=`. `make
db-up` для удобства даёт роль владельца — это разработка, не бой.

**Секреты передаются путём к файлу, а не значением.** Это касается и строки
подключения: в ней пароль базы. Ключ подписи голов аудита —
закрытый ключ Ed25519; через переменную окружения он попадает в `/proc/PID/environ`,
в вывод `systemctl show`, а через `$(cat …)` в командной строке — в `ps` для всех
пользователей машины. Тот, кто его прочитает, подделает головы, и доказательная сила
цепочки исчезнет молча. Файл обязан быть `0600` или `0400`, иначе сервер откажется
его использовать.

### Сервер отказывается стартовать, если

| Условие | Почему это отказ, а не предупреждение |
|---|---|
| нет `ALERTING_DSN_FILE` / `ALERTING_DSN` | подключаться некуда. Пустая база больше не создаётся молча |
| версия схемы не та, под которую собран релиз | иначе узел упал бы на первом запросе, которому нужна отсутствующая колонка, — то есть посреди инцидента |
| нет `ALERTING_ROOT_PUBKEY` | без него нельзя проверить собственные бандлы |
| файл секрета доступен группе или всем | секрет, который читают все локальные пользователи, — не секрет |
| в лестнице эскалации есть канал без провайдера | он сообщал бы об успешной доставке, ничего не отправив. Снимается `ALERTING_ALLOW_STUB_CHANNELS=1` — **никогда в проде** |
| не найден файл лестницы эскалации | раньше молча подставлялась встроенная, и узел работал по другим каналам и таймингам, чем настроил оператор. Встроенную теперь надо запросить по имени: `ALERTING_ESCALATION_CONFIG=builtin` |

Без `ALERTING_SERVER_KEY_FILE` сервер работает, но головы уходят без подписи и теряют
доказательную силу — при старте будет предупреждение. Это сознательно не отказ:
оповещать важнее, чем иметь идеальный журнал.

**Обязательно: NTP на каждом узле** (допуск перекоса ±120 с, окно рукопожатия
устройства — 60 с). Отказ NTP — молчаливый полный отказ: валидные клиенты начнут
получать отказ в подключении.

### Чего в этой сборке ещё нет

`push`, `sms`, `voice` и сирена — **заглушки**: они возвращают статус `stub` и ничего
не отправляют. Реально доставляет только WebSocket. В дашборде подтверждений это видно
как `push:stub`, и `stub` нигде не считается доставкой.

## 2. Отдать приказ

```bash
alerting-approver propose EVAC.BUILDING --real --severity critical \
    --groups fire-wardens --text "Задымление, 3 этаж" --person p-001

alerting-approver sign <order_id> --person p-001     # первая подпись
alerting-approver sign <order_id> --person p-002     # кворум набран → рассылка

alerting-approver status <order_id>                  # кто подтвердил
```

`--real` или `--drill` обязательны: у флага учения нет значения по умолчанию нигде в
системе, включая командную строку.

Подписывающему клиент **сам пересчитывает канонические байты** из нагрузки и не
доверяет тому, что предлагает сервер. Подписант, который подписывает то, что ему
подсунули, делегировал свои полномочия серверу.

## 3. Отбой

```bash
alerting-approver cancel <order_id> --person p-003 --text "Очаг ликвидирован"
```

Отбой, как и запуск, подписывают двое разных ЛПР (ADR 0003): после первой подписи
он ждёт второго ЛПР без срока. Кто дал отбой, видно на экране у каждого исполнителя.

**Исполнителя учат: отбой не отменяет то, что он видит своими глазами.** Если пожар
виден — `cannot_comply` с причиной, и продолжать.

`cannot_comply` — это **отказ, а не подтверждение**: человек остаётся в списке
неподтвердивших, и лестница эскалации продолжает подниматься до дежурного, дублирующего
исполнителя и сирены. Именно ради этого случая ступени переназначения и существуют.

Ошибочный отбой перекрывается повторной выдачей приказа на полном кворуме.

## 4. Регистрация

```bash
alerting-executor enroll --person x-104 --org acme --home ~/.alerting
# ключ генерируется на устройстве; корневой ключ вводится с карточки, а не скачивается
alerting-executor sync --home ~/.alerting
```

Полная процедура — [02-trust-and-approval.md](02-trust-and-approval.md) §4.
Ключевой шаг, который нельзя пропускать: **регистрируемый сверяет свой `key_id` в
справочнике, не отходя от стола.**

## 5. Отзыв — цель 60 секунд

1. Убрать ключ из справочника, добавить в `revoked[]`.
2. Поднять `version`.
3. Подписать корневым ключом (нужны оба хранителя).
4. Опубликовать.

Клиенты отвергнут любой справочник с версией ниже максимальной виденной, поэтому
откатить их назад нельзя.

Отзыв закрывает **и HTTP**: сервер перечитывает и перепроверяет справочник на каждом
запросе, поэтому отозванный ключ перестаёт работать не только на сокете и в кворуме,
но и на любом вызове API. Это сознательно не кэшируется — кэш и был бы той задержкой,
которой у отзыва быть не должно.

Репетируется с секундомером раз в год. Если это занимает трое суток — криптография
декоративна.

## 6. Учения

```bash
export ALERTING_DRILL_SITES=hq      # ТОЛЬКО на время учения
alerting-approver propose MUSTER --drill --severity warning --sites hq --person p-003
```

Без этой переменной сирена **откажется** звучать для учебного приказа. Это сделано
намеренно: учение, включившее боевой паттерн, порождает настоящую эвакуацию.

После учения переменную убрать.

## 7. Проверка аудита

```bash
alerting-auditor verify --server http://127.0.0.1:8080
alerting-auditor pull   --server http://127.0.0.1:8080 --out chain.json
alerting-auditor verify --file chain.json
```

`--dsn` читает базу напрямую и существует для оператора на узле. **Аудитор им не
пользуется:** проверяющий с доступом к боевой базе доверяет той самой машине, чью
историю проверяет. Независимые пути — `--file` и `--server`.

В конце каждого учения — принудительно опубликовать голову (`POST /v1/audit/head`) и
разослать её аудиторам.

## 8. Когда система лежит

Напечатано на карточке и на каждом посту. Это не приложение — это основная процедура
на случай отказа.

1. **Телефонное дерево.** У каждого ЛПР печатный список из пяти человек; у каждого из
   них — свои пять.
2. **Опознание парой «вызов-отзыв» текущей смены.** Меняется ежемесячно, раздаётся
   вместе с кодовой книгой. Именно она заменяет подпись, когда программной части нет.
3. **Повесить трубку и перезвонить по номеру, напечатанному на карточке.** Никогда по
   номеру, с которого позвонили. Одно это снимает большую часть голосового фишинга.
4. **Сирена с ручной панели** в дежурке — она не сблокирована с софтом именно ради
   этого случая.
5. **Всё записывается на бумаге** — время, кто, что — и в течение суток вносится в
   журнал событием `manual.backfill` за подписью вносящего, чтобы запись пережила
   инцидент.

## 9. Дежурные проверки

| Что | Как часто | Почему |
|---|---|---|
| `/v1/readyz` зелёный | непрерывно | узел бывает «жив» и при этом неспособен разослать приказ |
| Спул аудита пуст (`spool/`) | ежедневно | непустой спул означает, что записи журнала падали |
| Голова аудита опубликована | ежечасно | перестала производиться доказательная база |
| Смещение часов < 30 с | непрерывно | на 60 с валидные клиенты начнут получать отказ |
| Резервная копия отработала | ежедневно | ненулевой выход скрипта — тревога |
| Медиана времени от `quorum.met` до 90 % подтверждений | по каждому учению | главная метрика, см. ниже |
| Справочник моложе 7 суток | еженедельно | устаревший реестр показывается баннером, но не блокирует |
| Учебное восстановление из копии | ежеквартально | копия, которую не восстанавливали, — это надежда, а не копия |
| `GET /v1/channels/health` — список `silent` пуст | непрерывно | замолчавший канал должен стать заметен **до** ЧП. Это единственное, что есть против намеренного подавления, кроме телефонного дерева |
| `alerting_canary_ok` = 1 в `/v1/metricsz` | непрерывно | последний учебный приказ не дошёл. Это ближе к правде, чем `readyz`: тот говорит «узел исправен», а канарейка — «приказ бы ушёл прямо сейчас» |
| `alerting_canary_age_seconds` < 2 часов | непрерывно | канарейка не провалилась, а перестала запускаться. Отсутствие плохих новостей здесь не новость |
| Реплика базы на месте и не отстаёт | непрерывно | `alerting_replication_standbys`, `alerting_replication_lag_bytes`, и обязательно `alerting_replication_lag_unknown` = 0: ненулевое значение означает, что отставание не измеряется вовсе. Подробности и пороги — [`docs/10-failover.md`](10-failover.md) §4 |
| Учение переключения на резерв | ежеквартально | `deploy/postgres/failover-drill.sh`. Резерв, на который не переключались, — это надежда, ровно как и невосстановленная копия |

**Про `silent` без иллюзий.** Пока провайдеры заглушены, `push`, `sms`, `voice` и
сирена всегда в этом списке — их зонд отвечает `stub`, потому что сообщать о здоровье,
которого нет, хуже, чем не сообщать ничего. Реально наблюдается один канал: `ws`, и
его отказ означает «ни одного подключённого устройства исполнителя». Дежурный следит
именно за ним; остальные четыре уйдут из списка вместе с появлением провайдеров.

Состояние `stale` — отдельная и худшая беда: значит, перестал работать сам heartbeat,
и молчание больше ничего не означает.

**Главная метрика: медиана времени от набора кворума до 90 % подтверждений.** Растёт —
система гниёт.

Чем её посчитать — раньше в этом документе не было сказано ничем, и посчитать её было
нечем: у записи `order.dispatched` не было числа получателей, то есть знаменателя, без
которого «90 %» не определено. Теперь считается, и одним и тем же кодом в двух местах:

```
alerting-auditor report --dsn "$DSN"                      # пять последних приказов
alerting-auditor report --dsn "$DSN" --order-id <uuid>     # один конкретный
```

Печатается по каждому приказу: время до 90 % подтверждений, медиана и сколько человек
из скольких ответило. Те же числа отдаёт `/v1/metricsz` —
`alerting_ack_median_seconds` и `alerting_ack_share_seconds`.

**Когда метрика отвечает «неизвестно», это не ноль.** Приказ, разосланный до появления
счётчика получателей, печатается как `unknown (chain has no recipient count)`, а в
метриках попадает в `alerting_ack_share_unknown`. Ноль на его месте выдал бы худший
случай за лучший.

**Считается по приказам поимённо, а не одним числом по всем.** Учение на восемь человек
и учение на восемьсот — разные измерения, и общая медиана спрятала бы ровно тот тренд,
ради которого метрика заведена.
