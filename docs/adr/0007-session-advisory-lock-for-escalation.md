# ADR 0007. Один «восходящий» по лестнице — сессионная advisory-блокировка

**Статус:** принято (фаза 3).

## Контекст

Каждый узел запускает воркер эскалации. Если их несколько, по одной и той же лестнице
одновременно поднимаются несколько процессов: они читают одни приказы, рассылают по одним
каналам и гоняются за каждой заявкой.

Заявки в базе (`escalation_state` по людям, `escalation_extra` по ролям и группам)
делают повторную ступень невозможной. Но опираться только на них — значит выбрать
конструкцию, где нормальный режим работы это гонка, и корректность держится на том,
что все до единого пути прошли через заявку. Один восходящий делает обычный случай
простым, а заявки — подстраховкой, а не несущей конструкцией.

## Решение

Сессионная advisory-блокировка PostgreSQL (`pg_try_advisory_lock`) на отдельном
соединении. Лидер запрашивает её в начале **каждого** тика, а не один раз при старте.

## Почему не аренда в таблице

Аренда (строка `leader` с `expires_at`) требует трёх вещей, и каждую легко испортить
в компоненте, чей отказ молчалив:

- сердцебиение, которое надо продлевать чаще, чем истекает аренда;
- согласие двух сторон о времени — а расхождение часов здесь уже названо причиной
  молчаливого полного отказа (`docs/09-deployment.md` §2);
- правило для случая «держатель не умер, а просто затормозил».

PostgreSQL снимает сессионную блокировку в тот момент, когда пропадает соединение
держателя — включая исчезновение его машины, — и делает это, ни у кого не спрашивая
время. Это ровно то свойство, ради которого аренду обычно и пишут.

## Следствия

- **Отдельное соединение.** Блокировка сессионная, а соединение из пула возвращается
  после каждого запроса — это сняло бы её немедленно.
- **Запрос на каждом тике** даёт автоматическое переключение: умер держатель — упало
  соединение — следующий же спросивший стал лидером. Цена — один дешёвый запрос в тик.
- **Освобождение при остановке.** Перезапускающийся узел, который держал бы блокировку
  до таймаута соединения, оставляет все остальные узлы простаивать — то есть по лестнице
  никто не поднимается. `AppServices.close()` освобождает её явно.
- **Недоступность базы = не лидер.** Без базы всё равно нечего заявить, записать и
  подтвердить, так что подниматься по лестнице вслепую незачем.
- Заявки остаются. Тест `test_a_role_rung_notifies_once_even_with_two_climbers`
  намеренно отключает выбор лидера и требует, чтобы ступень всё равно сработала один
  раз: если выбор лидера когда-нибудь откажет, система не должна звонить дежурному
  дважды.
