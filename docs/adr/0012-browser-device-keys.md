# ADR 0012. Ключ ЛПР — в его браузере, панель получает только подписи

**Статус:** принято

## Контекст

Панель дежурного и ЛПР открывается по ссылке, в том числе извне и с iPad. До этого
решения она расшифровывала ключи людей **у себя**: ключи всех лежали на сервере в
томе `clients`, пароль открывал ключ в процессе панели. Это сводило защиту к паролям
(знать пароли двух ЛПР — значит отдать боевой приказ) и позволяло тому, кто управляет
сервером, подписывать за людей — то, от чего проект защищается с самого начала
(ADR 0004, полудоверенный сервер).

Нужно: UI по ссылке, на телефоне и планшете, без установки программ — и при этом
подпись невозможна без устройства человека.

## Решение

1. **Ключ создаётся в браузере** (WebCrypto Ed25519) на экране «Зарегистрировать это
   устройство». Хранится только зашифрованным: AES-GCM под ключом из пароля (PBKDF2,
   600 000 итераций). При входе разворачивается в **неизвлекаемый** `CryptoKey` и живёт
   в памяти страницы до её закрытия. Публичная часть вносится в справочник обычным
   порядком (хранители, `alerting-org directory add`).
2. **Доверенность на сеанс.** Панель создаёт сеансовый ключ и даёт браузеру
   подписать доверенность (`type: session-delegation`, свой домен подписи): `org_id`,
   `key_id` и `person_id` устройства, публичный сеансовый ключ, срок не больше 12 ч.
   Браузер проверяет, что это доверенность для его ключа и на ограниченный срок.
   HTTP-запросы панель подписывает сеансовым ключом и прикладывает доверенность
   (заголовок `Alerting-Delegation`); сервер проверяет её на каждом запросе по
   текущему справочнику и отзывам.
3. **Приказы подписывает только ключ устройства, в браузере.** Экран подписи
   строится из самого приказа, его отпечаток браузер считает сам и сверяет с
   панелью; подписывается тот же объект, что показан. Панель проверяет подпись по
   справочнику и только затем отправляет. Сервер проверяет подписи приказов по ключу
   устройства — сеансовый ключ подписать приказ не может.
4. **Канонизация — одна на двоих.** JCS в `devicekey.js` повторяет
   `alerting.core.canonical`; `tests/unit/test_devicekey_js.py` гоняет оба на одних
   данных (NFC, порядок по UTF-16, экранирование, отказ на null/float/больших числах).
5. **CSP:** скрипты только с адреса панели, без встроенного кода и `eval`.
6. Демо-вход с ключами на сервере остаётся за флагом для стенда.

## Последствия

- Пароль без устройства бесполезен; захват процесса панели или сервера не даёт
  подписать приказ. Отзыв ключа устройства обрывает его сеансы на следующем запросе.
- Работает на iPhone/iPad (Safari 17+), Android, настольных браузерах. Только https://
  или localhost — WebCrypto недоступен на http по сети.
- Каждое устройство — свой ключ. Очистка данных Safari, частный режим, чужое
  устройство — ключа нет; повторная регистрация. На iOS панель нужно добавить на
  экран «Домой», иначе Safari может стереть данные сайта через неделю без посещений.

## Чего это не закрывает

**Тот, кто подменит сам код страницы** (контроль над процессом панели или прокси с
TLS), может отдать браузеру скрипт, который попросит открытый ключ подписать другой
приказ, пока человек вошёл. Это предел любого веб-приложения. Смягчают: CSP, панель
на отдельном имени и отдельной машине от API, кворум из двух людей на двух
устройствах. Закрывает полностью только подпись вне браузера: нативное приложение
или аппаратный ключ (passkey / WebAuthn с Face ID) с отображением приказа самим
устройством — следующий шаг. Сделан в ADR 0016: приложение ЛПР, страница внутри сборки, ключ под
биометрией в Keychain / Keystore.

## Отвергнутые варианты

- **Ключи на сервере, вход паролем** (как было): см. контекст.
- **Подписывать в браузере каждый HTTP-запрос ключом устройства.** Пришлось бы
  переносить в браузер всю серверную часть панели. Доверенность даёт то же свойство —
  подпись приказа только на устройстве — малой ценой.
- **Passkey сразу.** WebAuthn подписывает свой формат (authenticatorData +
  clientDataJSON), не наши байты: потребовалось бы менять проверку приказов на всех
  устройствах. Оставлено вторым этапом.
