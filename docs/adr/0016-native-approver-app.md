# ADR 0016. Приложение ЛПР: ключ устройства под биометрией, страница — внутри приложения

**Статус:** принято

## Контекст

ADR 0012 перенёс ключ ЛПР с сервера в браузер: ключ Ed25519 создаётся на устройстве,
хранится зашифрованным под пароль и разворачивается в неизвлекаемый `CryptoKey` на
время сеанса. Две слабости он назвал сам:

1. **Код страницы приходит с сервера панели.** Тот, кто подменит его (контроль над
   процессом панели, прокси с TLS), отдаст браузеру скрипт, который попросит открытый
   ключ подписать другой приказ, пока человек вошёл. Это предел веб-приложения, и
   закрывает его только подпись вне страницы, присланной сервером.
2. **Ключ открывает пароль.** Пароль подсматривают и подбирают; открытый ключ живёт в
   памяти страницы весь сеанс и подписывает любой приказ без участия человека.

Нужно мобильное приложение для ЛПР, где подписать приказ без самого человека нельзя.

## Решение

1. **Нативное приложение на Capacitor** (`apps/approver/`) — так же, как приложение
   helpdesk. Отличие принципиальное: в helpdesk биометрия только запирает сохранённый
   вход и спрашивается при запуске; здесь она стоит **на каждой операции с ключом**.

2. **Страница — часть сборки приложения, не загружается с сервера.** `server.url` в
   `capacitor.config.json` нет, сетевых скриптов и `eval` нет (CSP `script-src
   'self'`), отладка WebView в релизе выключена. **Live update не используется**:
   изменение страницы — это новая сборка через магазин. Иначе подмена кода вернулась
   бы через обновление интерфейса — ровно та дыра, которую приложение закрывает.
   Сторожит `apps/approver/test/shipping.test.mjs`.

3. **Ключ хранит операционная система и выдаёт его только после биометрии.**
   Плагин `plugins/device-vault`:
   - **iOS:** элемент Keychain с `SecAccessControl(.biometryCurrentSet)` и
     `WhenPasscodeSetThisDeviceOnly`. Код-пароль запасным путём не служит (кнопки
     «Ввести пароль» нет): подсмотревший код подписать не сможет. Не попадает в
     резервную копию и на другой телефон.
   - **Android:** ключ Ed25519 зашифрован AES-256-GCM ключом из Android Keystore
     (StrongBox, если есть). Этот ключ доступен только после **сильной** биометрии
     (class 3), на одну операцию — шифр привязан к запросу через `CryptoObject`;
     PIN экрана не подходит.
   - **Смена набора отпечатков или лиц делает ключ недоступным навсегда**
     (`.biometryCurrentSet`, `setInvalidatedByBiometricEnrollment`). Путь назад —
     новый ключ и регистрация у хранителей. Это защита, а не сбой: иначе тот, кто
     знает код телефона, добавил бы свой отпечаток и подписывал бы им.

4. **Ключ покидает хранилище на одну операцию.** Вход (подпись доверенности),
   подпись приказа и продление сеанса — каждая спрашивает биометрию; системный
   запрос называет операцию («Подписать — БОЕВОЕ: Полная эвакуация здания»). Ключ
   импортируется в неизвлекаемый `CryptoKey`, подписывает и отпускается; между
   операциями его нет нигде, кроме хранилища ОС.

5. **Биометрия спрашивается только по нажатию человека.** Продление доверенности
   (12 ч) приложение не делает само — показывает кнопку «Продлить». Запрос Face ID,
   появляющийся сам, приучает подтверждать запросы не читая.

6. **Подпись — тот же Ed25519 и те же байты, что у панели.** `devicekey.js` берётся из
   панели как есть (`scripts/build.mjs`), экран проверки строится общим
   `DeviceKey.describe`, сверка отпечатка — `DeviceKey.reviewProblems`. Проверка
   приказов на сервере и у исполнителей не меняется.

7. **Панель — тот же сервер для приложения.** Страница живёт на
   `capacitor://localhost` (iOS) / `https://localhost` (Android), cookie панели туда не
   приходит. Поэтому `POST /api/device/finish` с заголовком `X-Alerting-Client: app`
   отдаёт токен сеанса в теле, а приложение шлёт его как `Authorization: Bearer`.
   CORS отвечает только этим двум origin'ам (`--app-origins`, пусто — приложение
   выключено), без `allow_credentials`. Токен хранится только в памяти: после
   перезапуска приложения — снова вход по биометрии.

8. **Приложение — только для ЛПР.** Дежурному панель отказывает на входе приложения
   (403): справочник, контакты и хранители остаются в панели.

## Почему ключ Ed25519 не в Secure Enclave

Secure Enclave и большинство StrongBox умеют только P-256. Ключ, который нельзя
извлечь даже со взломанного телефона, означал бы смену алгоритма подписи приказов —
`core/signing.py`, справочник, проверка на всех устройствах исполнителей. Сейчас
аппаратно защищён доступ (биометрия решает ОС, а не приложение), а сам ключ на время
операции попадает в память приложения. Это осознанный компромисс; переход на P-256 в
Secure Enclave — отдельное решение, если модель угроз потребует защиты от
взломанного (jailbreak/root) телефона.

## Что это закрывает

- Подмена кода панели или сервера: страница подписи не приходит с сервера.
- Подсмотренный пароль или код телефона: без биометрии ключа нет.
- Подпись «в фоне» при открытом сеансе: каждая подпись требует биометрии.
- Добавленный чужой отпечаток: ключ становится недоступен.

## Чего это не закрывает

- **Взломанный телефон** (jailbreak/root с внедрением кода в процесс приложения):
  ключ на время операции в памяти приложения — см. выше.
- **Человек подписывает под принуждением.** Против этого — кворум из двух разных ЛПР.
- **Сервер задерживает или подавляет приказ** — как и раньше (ADR 0004).
- **Push.** Канал `push` пока без провайдера (FCM/APNs); о предложении на подпись ЛПР
  узнаёт, открыв приложение. Подключение push — следующий шаг; в уведомлении, как и
  в SMS, только «откройте приложение».

## Последствия

- Регистрация устройства как в ADR 0012: ключ создаётся в приложении, публичную часть
  ЛПР передаёт регистрирующему, хранители вносят её в справочник.
- Сменил отпечатки, удалил приложение, сменил телефон — новый ключ и новая регистрация;
  старый ключ отзывают в справочнике.
- Обновление приложения — только через магазин. Номер `appId` (`me.yamal.alerting`)
  после выхода в магазины не меняется.
- Нужен iOS 17+ и Android с WebView, умеющим Ed25519 в WebCrypto; иначе приложение
  говорит об этом словами при запуске.

## Отвергнутые варианты

- **Обернуть веб-панель в приложение с `server.url`.** Код приходит с сервера — первая
  слабость остаётся.
- **Live update, как в helpdesk.** То же самое через обновление интерфейса.
- **Программный гейт биометрии перед чтением из обычного защищённого хранилища (как в
  helpdesk).** Решение принимает код приложения, а не ОС; подменённый код гейт обходит.
- **Passkey / WebAuthn.** Подписывает свой формат (authenticatorData + clientDataJSON),
  не наши байты — менять проверку на всех устройствах (как и в ADR 0012).
