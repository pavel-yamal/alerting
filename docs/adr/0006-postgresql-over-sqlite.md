# ADR 0006. PostgreSQL вместо SQLite, сырой SQL остаётся

**Статус:** принято. Отменяет [ADR 0002](0002-sqlite3-over-sqlalchemy.md) в части
движка и **сохраняет** её в части отказа от ORM.

## Контекст

ADR 0002 назвала свой собственный путь выхода: «SQLAlchemy + PostgreSQL, когда
понадобится несколько узлов». Половина этого предсказания сбылась. Несколько узлов
действительно понадобились — это фазы 6–7 плана, и база на локальном диске делает их
невозможными не в принципе, а буквально. Вторая половина не сбылась: ORM не нужен и
сейчас.

Помимо нескольких узлов SQLite упиралась и в одном процессе. Воркер эскалации и
обработчики HTTP делят одно соединение и чередуются на нём через `await`; пока всё
было в автокоммите, это сходило с рук, но любая транзакция сделала бы их общими.

## Решение

PostgreSQL 16, драйвер psycopg 3 с пулом соединений. **Сырой SQL остаётся**, весь в
`server/db/repo.py`. Версионированные миграции в `server/db/migrations/`. Журнал
только на добавление обеспечивается **двумя** механизмами: правами роли и триггерами.

## Почему не ORM

Причина из ADR 0002 не изменилась и стала весомее. Система, весь смысл которой в
прослеживаемости, не должна прятать свои записи за маппером: рецензент безопасности
должен видеть каждую команду, касающуюся `audit_log`, и убедиться, что пути `UPDATE`
и `DELETE` просто нет. Тринадцать таблиц по-прежнему не требуют ORM, а advisory-
блокировки и `ON CONFLICT`, на которых теперь держится корректность, через маппер
выражаются хуже, чем напрямую.

## Почему две роли, а не только триггеры

Триггеры ловят неосторожность. Они **не ловят `TRUNCATE`** (он обходит строчные
триггеры) и их может отключить владелец таблицы. Поэтому сервер подключается ролью
`alerting_app`, у которой по `audit_log` есть только `SELECT` и `INSERT`:

| Слой | От кого защищает |
|---|---|
| права `alerting_app` | **полностью скомпрометированный процесс сервера** — он не имеет права даже попытаться |
| триггеры | владельца: администратора с консолью в три часа ночи |
| хеш-цепочка и внешние головы | владельца с намерением — единственное, что действительно работает против него |

Это не избыточность: каждый слой ловит то, что пропускают остальные.

## Почему автокоммит по умолчанию

Пул открывается в режиме автокоммита, а транзакции берутся явно и только в трёх
местах. Это сохраняет семантику SQLite один в один — и сохраняет свойство, ради
которого в `AuditService` вообще есть спул.

В PostgreSQL отказавший запрос переводит транзакцию в `aborted`, и каждый следующий
запрос падает до отката. `AuditService.append` ловит любую ошибку, пишет запись на
диск и **возвращается, чтобы рассылка продолжилась** — «логгер никогда не блокирует
оповещение». При транзакции по умолчанию переживаемый отказ журнала превратился бы в
несостоявшееся оповещение. Ровно тот исход, ради предотвращения которого спул и
написан.

Тест на это свойство пришлось переписать: он подменял `RuntimeError`, который до базы
не доходил, и **продолжал бы проходить, пока свойство регрессировало**.

## Что это стоило

- **База стала внешней зависимостью.** `make demo` больше не работает на пустой
  машине: нужен `make db-up`. Это цена за то, что демо проверяет ту же конфигурацию,
  что и бой.
- **`rm файла` больше не «удалить базу».** `org_init` и учебное восстановление теперь
  требуют прав. Это, скорее, приобретение: на SQLite опечатка в пути позволяла
  уничтожить боевую цепочку аудита через `rm`.
- **Появился контракт миграций.** Откат релиза больше не безопасен автоматически —
  см. `docs/09-deployment.md` §6, только расширяющие миграции.
- **Аудитору больше не отдать файл.** Независимая проверка идёт через `--file`
  (выгрузка) или `--server`. Это тоже скорее приобретение: аудитор с доступом к
  боевой базе доверяет той самой машине, чью историю проверяет.

## Следствия

- `Repo` содержит весь SQL; за его пределами SQL нет. В `Repo` **намеренно
  отсутствуют** методы обновления и удаления для `audit_log`.
- Миграции применяет отдельная команда (`alerting-server migrate`) из юнита
  `Type=oneshot` ролью владельца. Приложение только **проверяет** версию схемы и
  отказывается стартовать при расхождении.
- Каждый `ORDER BY` заканчивается уникальной колонкой. SQLite разрешала ничью по
  rowid, и две выборки — те, что решают, какие приказы эскалируются и какие
  проверяются на повтор, — опирались на это по случайности.
- Счётчик `seq` во внешнюю согласованную последовательность, как предсказывала
  ADR 0002, ещё **не** вынесен: это фаза 3. Пока его защищает транзакция вокруг
  `next_seq` + `create_proposal` и ограничение `UNIQUE (stream_id, seq)`.
